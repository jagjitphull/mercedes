iptables vs nftables

Both configure Linux Netfilter, but they expose different rule-management models. On modern Ubuntu, the familiar iptables command may itself use the nftables backend; that compatibility layer is not the same as writing native nft syntax.

Operational rule: choose one management authority for a ruleset. Mixing native nft, UFW, firewalld, Docker-generated rules, and manual iptables commands without a design can create surprising behavior.

The four-level mental model

Think of nftables as a company security system: a ruleset contains departments, each department has checkpoints, and each checkpoint has ordered instructions.

1

Ruleset

Everything currently loaded into nftables.

2

Table

Administrative container, scoped to a family such as inet.

3

Chain

Ordered rules. A base chain connects to a kernel hook.

4

Rule

Matches expressions, then performs statements or a verdict.

🏢

Table = security department

For example, an inet training table can hold the whole training policy without touching unrelated tables.

🚪

Base chain = connected checkpoint

A base chain has a type, hook, priority, and optional default policy.

📋

Rule = ordered instruction

Example: “when TCP destination port is 22, count and accept.” Rules are normally evaluated from top to bottom.

⚖️

Verdict = decision

accept, drop, reject, jump, goto, return, or queue.

table inet training {
    chain input {
        type filter hook input priority filter; policy drop;

        iifname "lo" accept
        ct state invalid drop
        ct state established,related accept
        tcp dport 22 counter accept
    }
}
Read it aloud: “Create an IPv4/IPv6 table named training. Attach an input filter at priority 0. Drop unmatched traffic, except loopback, valid return traffic, and SSH.”

Hooks and packet journey

A hook is a point in the kernel networking path where a base chain can inspect a packet. The important route depends on whether the packet is addressed to this host, created by this host, or routed through this host.

INPUT

Traffic whose final destination is the local machine: SSH to the VM, HTTP to a local service, ping to a local address.

OUTPUT

Traffic generated by a local process: curl, package updates, DNS queries, an application calling an API.

FORWARD

Traffic routed through the machine: a gateway, router, VPN concentrator, container host, or segmented appliance.

Common mistake: placing a rule in INPUT to control a packet that is merely passing through the host. Routed traffic uses FORWARD, not INPUT.

Priorities: who runs first?

Multiple base chains can register at the same hook. Lower numeric priority runs earlier. The common symbolic priority filter equals 0.

Set a priority, then show the evaluation order.
−300

raw

Very early. Used for tasks such as disabling connection tracking before lookup.

0

filter

The normal priority for packet filtering.

50

security

Runs after standard filter priority at the same hook.

Important nuance: an accept verdict ends the current chain, but a later base chain at the same hook can still drop the packet. A drop verdict is final for that packet.

Build a safe host firewall

A practical policy starts with traffic classes: loopback, malformed/invalid traffic, established return traffic, explicitly permitted new services, then a default policy.

Interactive rule builder

Generated command

Recommended baseline

#!/usr/sbin/nft -f
destroy table inet training

table inet training {
    chain input {
        type filter hook input priority filter; policy drop;
        iifname "lo" counter accept comment "loopback"
        ct state invalid counter drop comment "invalid traffic"
        ct state established,related counter accept comment "return traffic"
        ip protocol icmp counter accept comment "IPv4 diagnostics"
        meta l4proto ipv6-icmp counter accept comment "IPv6 ICMP control traffic"
        tcp dport 22 ct state new counter accept comment "SSH"
        limit rate 5/minute burst 10 packets log prefix "NFT_INPUT_DROP: " level warning
    }

    chain output {
        type filter hook output priority filter; policy accept;
    }

    chain forward {
        type filter hook forward priority filter; policy drop;
        ct state invalid counter drop
        ct state established,related counter accept
    }
}
Remote-server warning: never activate a default-drop INPUT policy over SSH unless the current SSH path is explicitly allowed and a tested rollback mechanism is armed.

Connection tracking: memory for the firewall

Connection tracking lets the kernel classify packets using context, not just isolated header fields. The common rule ct state established,related accept permits legitimate return or helper-related traffic without opening every high port.

NEW

Beginning a tracked flow.

ESTABLISHED

Part of a known bidirectional flow.

RELATED

New flow associated with an existing one.

INVALID

Cannot be identified or tracked correctly.

Select a sequence.

NEW does not mean “only SYN”

It means conntrack sees the packet as starting or belonging to a flow that has not yet become established. Protocol behavior and conntrack settings matter.

INVALID should normally be dropped early

Invalid packets can be malformed, out of the expected state window, or untrackable. Log them only with rate limiting to avoid flooding.

ct state invalid counter drop
ct state established,related counter accept

Filter local traffic by UID/GID

meta skuid and meta skgid match the UID or GID associated with the originating socket. Their clearest use is in an OUTPUT chain for traffic created by local processes.

Scope limit: these expressions identify the owner of a local originating socket. They are not a general way to identify remote users, and they are not appropriate for ordinary forwarded traffic.
Select a process and evaluate it.
# Resolve the numeric UID, then block HTTP/HTTPS created by that account.
BLOCK_UID=$(id -u labblocked)
sudo nft add rule inet training output \
  meta skuid "$BLOCK_UID" tcp dport { 80, 443 } \
  counter reject with tcp reset

# Equivalent group-based match.
BLOCK_GID=$(getent group labblocked | cut -d: -f3)
sudo nft add rule inet training output \
  meta skgid "$BLOCK_GID" tcp dport { 80, 443 } \
  counter reject with tcp reset

Trace the real rule path

nft monitor trace answers the question counters cannot: “which chains and rules did this packet traverse?” A packet must first be marked for tracing with meta nftrace set 1. Keep the match narrow because broad tracing can be noisy.

Safe, selective trace rule

# Mark only the lab port for tracing. No verdict means evaluation continues.
sudo nft insert rule inet training input \
  tcp dport 65000 meta nftrace set 1 \
  comment "temporary trace marker"

# Terminal 1: display trace events.
sudo nft monitor trace

# Terminal 2: confirm packet arrival independently.
sudo tcpdump -ni any 'tcp port 65000'

# From the host or a second VM:
nc -vz -w 2 VM_IP 65000 || true

Remove the temporary marker

# Find the handle of the temporary rule.
sudo nft -a list chain inet training input

# Replace HANDLE with the displayed number.
sudo nft delete rule inet training input handle HANDLE

IPv4, IPv6 and table families

The table family determines which packets can enter the table. An inet table can hold shared IPv4 and IPv6 policy, but address expressions remain protocol-specific: ip saddr is IPv4 and ip6 saddr is IPv6.

inet

IPv4 + IPv6. Usually the cleanest choice for a dual-stack host firewall.

ip / ip6

IPv4-only or IPv6-only policy when separate rulesets are intentional.

arp

ARP packet filtering for IPv4 address-to-MAC resolution traffic.

bridge

Frames traversing a Linux bridge, including bridged IP traffic.

netdev

Early ingress processing attached to a network device.

Important

Blocking IPv4 does not automatically secure an independently defined IPv6 ruleset.

Choose a family and packet.
table inet dual_stack {
  set admin4 { type ipv4_addr; flags interval; elements = { 192.0.2.0/24 } }
  set admin6 { type ipv6_addr; flags interval; elements = { 2001:db8:10::/64 } }

  chain input {
    type filter hook input priority filter; policy drop;
    ct state established,related accept
    ip protocol icmp accept
    meta l4proto ipv6-icmp accept
    ip saddr @admin4 tcp dport 22 accept
    ip6 saddr @admin6 tcp dport 22 accept
  }
}
Do not blanket-drop ICMPv6. IPv6 relies on ICMPv6 for essential control functions, including neighbor discovery and path-MTU handling. Design a deliberate ICMPv6 policy instead.

Named sets and maps

Sets replace repeated rules with one efficient membership lookup. Maps associate a key with data; verdict maps can map ports or addresses directly to actions.

Named address and service sets

table inet policy {
  set admin4 {
    type ipv4_addr
    flags interval
    elements = { 192.0.2.10, 198.51.100.0/24 }
  }

  set web_ports {
    type inet_service
    elements = { 80, 443 }
  }

  chain input {
    type filter hook input priority filter; policy drop;
    ip saddr @admin4 tcp dport @web_ports counter accept
  }
}

Verdict map

table inet service_map {
  map service_verdicts {
    type inet_service : verdict
    elements = { 22 : accept, 80 : accept, 443 : accept }
  }

  chain input {
    type filter hook input priority filter; policy drop;
    tcp dport vmap @service_verdicts
  }
}

One lookup replaces several nearly identical port rules. Use comments and conservative naming so compact policy remains readable.

Validate, export, restore, persist

Treat a ruleset like production configuration: back up first, validate syntax without applying it, load in one transaction, verify, and keep a rollback path.

# 1. Back up the active ruleset.
sudo nft list ruleset | sudo tee /root/nft-before-lab.nft >/dev/null

# 2. Validate a candidate without changing the kernel ruleset.
sudo nft --check --file ./training.nft

# 3. Apply the complete file transactionally.
sudo nft --file ./training.nft

# 4. Verify rules, handles and counters.
sudo nft --numeric --handle list ruleset

# 5. Export the current result.
sudo nft list ruleset | sudo tee /root/nft-after-lab.nft >/dev/null
sudo install -m 0600 ./training.nft /etc/nftables.conf
sudo nft --check --file /etc/nftables.conf
sudo systemctl enable nftables.service
sudo systemctl restart nftables.service
sudo systemctl status nftables.service --no-pager
sudo nft list ruleset
Before replacing /etc/nftables.conf, inspect the existing file and confirm no other firewall manager owns it.
sudo tee /root/nft-rollback.sh >/dev/null <<'SCRIPT'
#!/bin/sh
nft flush ruleset
nft -f /root/nft-before-lab.nft
SCRIPT
sudo chmod 700 /root/nft-rollback.sh

# Schedule automatic rollback in five minutes.
sudo systemd-run --unit=nft-rollback --on-active=5m \
  /root/nft-rollback.sh

# After successful verification, cancel the timer.
sudo systemctl stop nft-rollback.timer

Diagnose the layer, not your hunch

A failed connection does not prove a firewall problem. Walk the stack in order: name resolution, routing, packet visibility, nftables verdict, listening socket, then application behavior.

Select a fault and begin.

Core command kit

getent ahosts example.com
ip route get 203.0.113.10
sudo tcpdump -ni any 'host 203.0.113.10'
sudo nft monitor trace
sudo ss -lntup
curl -vk https://example.com
sudo journalctl -u SERVICE --since '-10 minutes'

Interpretation rules

  • No packet in tcpdump: investigate DNS, route, sender or upstream network first.
  • Packet visible + trace drop: nftables policy is the immediate blocker.
  • Trace accepts + no listener: start or reconfigure the service.
  • TCP connects + HTTP/TLS fails: inspect the application, certificate and authentication layers.

Broken-rule challenges

Predict the root cause before clicking. These are policy-logic failures; several will pass nft --check because syntactically valid does not mean operationally correct.

1 · The trusted SSH rule never works

tcp dport 22 drop
ip saddr 192.0.2.0/24 tcp dport 22 accept

2 · A routed client is not blocked

The administrator added the deny rule to INPUT, but the Linux host is routing the packet between two interfaces.

3 · Replies disappear after default-drop

New inbound SSH is allowed, but return traffic for locally initiated HTTPS requests is dropped.

4 · A rule has zero hits

iifname "eth0" tcp dport 22 accept

The VM interface is actually named ens3.

5 · IPv4 is blocked, but the service is still reachable

The application listens on both stacks. Only an ip family ruleset was created.

6 · FORWARD rules allow traffic, but routing still fails

The filter counters remain zero and the host is intended to act as a router.

Key lesson: nft --check --file validates parser and ruleset semantics; it cannot prove that rule order, interface names, routes, services or business intent are correct.

Create and inspect the object hierarchy

Table → base chain → rules.
sudo nft add table inet training
sudo nft 'add chain inet training input { type filter hook input priority filter; policy accept; }'
sudo nft add rule inet training input iifname lo counter accept comment 'loopback'
sudo nft -a list table inet training
Expected pattern:
table inet training {
    chain input {
        type filter hook input priority filter; policy accept;
        iifname "lo" counter packets 0 bytes 0 accept comment "loopback" # handle N
    }
}

Explain: inet covers IPv4 and IPv6. The chain becomes a base chain because it has a hook and priority. The handle is the kernel object identifier used for targeted deletion or replacement.

2

Stateful INPUT filtering without lockout

Apply a file only after syntax check.
cat > ~/training.nft <<'NFT'
destroy table inet training

table inet training {
  chain input {
    type filter hook input priority filter; policy drop;
    iifname "lo" counter accept
    ct state invalid counter drop
    ct state established,related counter accept
    ip protocol icmp counter accept
    meta l4proto ipv6-icmp counter accept
    tcp dport 22 ct state new counter accept
    limit rate 5/minute log prefix "NFT_INPUT_DROP: " level warning
  }
  chain output {
    type filter hook output priority filter; policy accept;
  }
}
NFT
sudo nft --check --file ~/training.nft
sudo nft --file ~/training.nft
sudo nft list table inet training
Expected: the check command exits silently with status 0. The loaded input chain shows policy drop and the explicit allow rules. Existing SSH remains possible because established traffic and TCP/22 are accepted.
Do not copy this to a remote production server unchanged. Source networks, interfaces, IPv6 requirements, management ports, and orchestration-generated rules must be designed first.

Repair a policy bug and clean up

Show why syntax validation and operational validation are separate.
cat > ~/shadowed.nft <<'NFT'
table inet shadow_demo {
  chain input {
    type filter hook input priority 10; policy accept;
    tcp dport 22 drop
    ip saddr 192.0.2.0/24 tcp dport 22 accept
  }
}
NFT

# This can pass: the logical ordering problem is not a syntax error.
sudo nft --check --file ~/shadowed.nft

# Fix by placing the specific allow before the general deny.
sed -i '/tcp dport 22 drop/d' ~/shadowed.nft
sed -i '/ip saddr/a\\    tcp dport 22 drop' ~/shadowed.nft

sudo nft --file /root/nft-before-lab.nft

Capstone: secure a dual-stack web server

Turn requirements into a testable policy. Use documentation addresses and a placeholder service UID in the supplied file; trainees must replace them with lab values before applying it.

Required outcomes

  1. Default-drop INPUT and FORWARD policy
  2. Loopback plus established/related traffic allowed
  3. Invalid traffic dropped
  4. SSH allowed only from the administration subnet
  5. HTTP and HTTPS allowed publicly
  6. IPv4 ICMP and essential ICMPv6 deliberately handled
  7. Denied traffic logged with rate limiting
  8. One service UID restricted to a specific HTTPS destination
  9. Ruleset syntax-checked, exported and recoverable
  10. Counters and trace output used as evidence
Before applying: replace 192.0.2.0/24, 203.0.113.10 and UID 991. These are documentation/example values, not a deployable production policy.

Reference solution

#!/usr/sbin/nft -f
destroy table inet capstone

table inet capstone {
  set admin4 {
    type ipv4_addr
    flags interval
    elements = { 192.0.2.0/24 }
  }
  set public_web { type inet_service; elements = { 80, 443 } }

  chain input {
    type filter hook input priority filter; policy drop;
    iifname "lo" counter accept
    ct state invalid counter drop
    ct state established,related counter accept
    ip protocol icmp limit rate 10/second counter accept
    meta l4proto ipv6-icmp limit rate 10/second counter accept
    ip saddr @admin4 tcp dport 22 ct state new counter accept
    tcp dport @public_web ct state new counter accept
    limit rate 5/minute burst 10 packets counter \
      log prefix "NFT_CAPSTONE_DROP: " level warning
  }

  chain output {
    type filter hook output priority filter; policy accept;
    ct state established,related counter accept
    meta skuid 991 jump app_egress
  }

  chain app_egress {
    ip daddr 203.0.113.10 tcp dport 443 ct state new counter accept
    counter reject
  }

  chain forward {
    type filter hook forward priority filter; policy drop;
    ct state invalid counter drop
    ct state established,related counter accept
  }
}

Glossary

Netfilter
Linux kernel framework that provides packet-processing hooks and subsystems.
nftables
Modern Netfilter packet classification and filtering framework.
nft
Userspace command-line utility for nftables.
Family
Protocol context of a table: inet, ip, ip6, arp, bridge, or netdev.
Base chain
A chain registered to a networking hook.
Regular chain
A chain used as a jump/goto target; it has no direct hook.
Hook
A point in the kernel packet path such as input, output, or forward.
Priority
Order among base chains on the same hook; lower runs earlier.
Policy
Base-chain action for packets that reach the end without a verdict.
Conntrack
Kernel subsystem that tracks flows and provides connection state.
Counter
Stateful packet and byte hit measurement.
nftrace
Per-packet trace flag that causes nftables trace events to be emitted.
Set
Named collection used for efficient membership matching.
Verdict map
Map whose values are actions such as accept, drop or jump.
