Network namespace concept

One kernel can present several independent views of networking.

🏢
Apartment-building analogy: The Linux kernel is the building. Each namespace is a locked apartment with its own doors (interfaces), address book (routes), intercom extensions (ports), and security desk (firewall). A veth pair is a cable connecting apartments or a shared lobby.
ResourcePer namespace?Meaning
InterfacesYesA device moved into one namespace disappears from the others.
IPv4/IPv6 routesYesEach namespace makes its own forwarding decision.
Listening portsYesTwo namespaces may both listen on TCP port 8080 without conflict.
Firewall rulesYesThe host and gateway namespace can have different nftables rulesets.
Loopback interfaceYeslo starts down in a newly created named namespace.

Network namespaces do not create a new machine. Processes still use the same Linux kernel, CPU, memory subsystem, and host storage unless other namespace or isolation mechanisms are added.

Security implication: A network namespace is strong network-stack isolation, not a complete hostile-workload sandbox by itself.
  • Container networking foundations.
  • Virtual routers, firewalls, and service meshes.
  • CI tests for network policy and routing.
  • Automotive Ethernet zone prototypes before hardware is available.
Create and inspect a namespace
sudo ip netns add demo
sudo ip netns list
sudo ip netns exec demo ip -br link
sudo ip netns exec demo ip route
sudo ip netns exec demo ss -lntup
sudo ip netns del demo
Key observation: A new namespace normally shows only lo, and that loopback interface must be brought up before local services behave normally.

Linux bridge: a software Layer-2 switch

A bridge forwards Ethernet frames by learning source MAC addresses.

Bridge behavior

  • Ports attached to the bridge share one broadcast domain.
  • Hosts in the same subnet can communicate without IP routing.
  • The bridge learns which MAC address is reachable through which port.
  • Unknown unicast and broadcast frames are flooded to eligible ports.
Bridge vs router: A bridge makes a Layer-2 forwarding decision using MAC addresses. A router makes a Layer-3 forwarding decision using destination IP prefixes. Do not enable ip_forward merely to make two same-subnet bridge members communicate.

Namespace routing and forwarding

Separate subnets need a router, and the router must be allowed to forward.

1. Endpoint route

Each ECU namespace needs a connected route and usually a default route through the gateway-side address.

2. Gateway interfaces

The gateway namespace owns one interface and IP address in each zone subnet.

3. Forwarding switch

net.ipv4.ip_forward=1 allows the namespace to route packets between interfaces.

Route decision simulator

Choose a source and destination, then inspect the route.
Two separate controls: Linux IP forwarding decides whether routing is possible. nftables decides whether a particular forwarded packet is permitted. Enabling one does not automatically configure the other.

Using namespaces to simulate ECU zones

Represent zones as independent IP stacks connected through a policy gateway.

🎵 Infotainment

Media, user apps, phone integration, displays.

Trust: Lower. Rich external input and large software surface.

📡 Telematics

Cellular connectivity, cloud services, remote commands, OTA channels.

Trust: Boundary zone. Exposed to external networks.

📷 ADAS

Sensor processing, perception, driver-assistance functions.

Trust: High integrity and availability requirements.

⚙️ Powertrain

Engine, transmission, propulsion, torque-related control paths.

Trust: Safety-critical; extremely restricted access.

Why this lab is useful in the real world

Architecture rehearsal

Test addressing, route design, service placement, and zone boundaries before physical ECUs and switches are available.

Security regression

Automate checks that forbidden paths remain blocked while approved service flows remain available after policy changes.

Incident exercises

Simulate a compromised infotainment workload attempting lateral movement toward ADAS or powertrain zones.

Training and demos

Make packet paths visible with tcpdump, nftables counters, and logs without requiring an automotive bench.

Design principle: “Same vehicle” does not imply “same trust.” The gateway should expose only explicitly required service paths, not general reachability.

Accuracy boundary: what the model proves—and what it does not

Shared-kernel limitation: All namespaces use the same Linux kernel. They are excellent for network-stack isolation and testing, but they are not equivalent to separate physical ECUs or separate virtual machines against a hostile kernel exploit.

Packet-policy simulator

Select a flow. This educational simulator mirrors the fixed ruleset below; it does not execute packets.
Gateway namespace nftables ruleset
sudo ip netns exec gw nft -f - <<'EOF'
flush ruleset

table inet zonefw {
  chain forward {
    type filter hook forward priority filter; policy drop;

    ct state invalid counter drop
    ct state established,related counter accept

    iifname "g-tcu"  oifname "g-info" tcp dport 8080 counter accept
    iifname "g-adas" oifname "g-pt"   tcp dport 8080 counter accept

    limit rate 5/second burst 10 packets counter log prefix "ZONE_DROP " flags all
    counter drop
  }
}
EOF

sudo ip netns exec gw nft list ruleset
Rule-flow order matters: invalid packets are dropped first, return packets are accepted next, narrowly approved new services follow, and all remaining traffic reaches the rate-limited logging rule plus final drop.
Why two final rules? The first rule rate-limits logging. The second rule drops every remaining packet, including packets above the logging rate, so excess traffic is still blocked without flooding the log.

Four-zone topology
# Create namespaces
for ns in info tcu adas pt gw; do sudo ip netns add "$ns"; done

# Create one veth pair per zone; move one end into the ECU zone and one into gw
sudo ip link add z-info type veth peer name g-info
sudo ip link add z-tcu  type veth peer name g-tcu
sudo ip link add z-adas type veth peer name g-adas
sudo ip link add z-pt   type veth peer name g-pt
sudo ip link set z-info netns info; sudo ip link set g-info netns gw
sudo ip link set z-tcu  netns tcu;  sudo ip link set g-tcu  netns gw
sudo ip link set z-adas netns adas; sudo ip link set g-adas netns gw
sudo ip link set z-pt   netns pt;   sudo ip link set g-pt   netns gw

# Bring up loopback interfaces
for ns in info tcu adas pt gw; do sudo ip -n "$ns" link set lo up; done

# Configure endpoint addresses
sudo ip -n info addr add 10.10.10.2/24 dev z-info
sudo ip -n tcu  addr add 10.10.20.2/24 dev z-tcu
sudo ip -n adas addr add 10.10.30.2/24 dev z-adas
sudo ip -n pt   addr add 10.10.40.2/24 dev z-pt
sudo ip -n info link set z-info up
sudo ip -n tcu  link set z-tcu up
sudo ip -n adas link set z-adas up
sudo ip -n pt   link set z-pt up

# Configure gateway-side addresses
sudo ip -n gw addr add 10.10.10.1/24 dev g-info
sudo ip -n gw addr add 10.10.20.1/24 dev g-tcu
sudo ip -n gw addr add 10.10.30.1/24 dev g-adas
sudo ip -n gw addr add 10.10.40.1/24 dev g-pt
for dev in g-info g-tcu g-adas g-pt; do sudo ip -n gw link set "$dev" up; done

# Add default routes in zone namespaces
sudo ip -n info route add default via 10.10.10.1
sudo ip -n tcu  route add default via 10.10.20.1
sudo ip -n adas route add default via 10.10.30.1
sudo ip -n pt   route add default via 10.10.40.1

# Enable forwarding only inside the gateway namespace
sudo ip netns exec gw sysctl -w net.ipv4.ip_forward=1

# Verify routes and routed reachability before applying firewall policy
sudo ip -n gw -br addr
sudo ip -n info route
sudo ip netns exec info ping -c 2 10.10.40.2

...

Fix: No such file or directory under zonefw

This message does not mean the nft executable is missing. It means the named nftables object is absent from the network namespace where the command ran. The policy may not have been applied, may have been applied in the host namespace, or the gw namespace may have been deleted and recreated.

# Gateway network namespace

    type filter hook forward priority filter; policy drop;
    ct state invalid counter drop
    ct state established,related counter accept
    iifname "g-tcu"  oifname "g-info" tcp dport 8080 counter accept
    iifname "g-adas" oifname "g-pt"   tcp dport 8080 counter accept

Failure-injection troubleshooting lab

Break one component at a time, predict the symptom, prove the cause, and restore the topology.

Lab rule: Inject only one fault at a time. Run the matching restore command before selecting another fault, or symptoms can overlap and mislead the diagnosis.
Fault command and safe restore

Correct nftables packet tracing

nft monitor trace displays only packets whose nftables trace flag has been enabled. The temporary chain below marks one blocked flow before the main firewall chain evaluates it.

Temporary nftrace chain
# Create a temporary earlier-priority trace chain
sudo ip netns exec gw nft delete table inet trace_lab 2>/dev/null || true
sudo ip netns exec gw nft 'add table inet trace_lab'
sudo ip netns exec gw nft   'add chain inet trace_lab forward_trace { type filter hook forward priority -20; policy accept; }'
sudo ip netns exec gw nft   'add rule inet trace_lab forward_trace ip saddr 10.10.10.2 ip daddr 10.10.40.2 meta nftrace set 1'

# Terminal A: watch rule-by-rule evaluation
sudo ip netns exec gw nft monitor trace

# Terminal B: generate the blocked flow
sudo ip netns exec info   curl --max-time 3 -I http://10.10.40.2:8080/

# Always remove the temporary tracing table
sudo ip netns exec gw nft delete table inet trace_lab

Policy requirements

  • Infotainment cannot initiate traffic to ADAS or Powertrain.
  • ADAS reaches exactly one approved Powertrain TCP service.
  • Powertrain cannot initiate new inter-zone sessions.

Troubleshooting decision guide

Start with link state, then addressing, routing, forwarding, and firewall policy.

Namespace exists, but only loopback is visible

The veth peer was not moved into the namespace, or the wrong namespace was inspected.

Check ownership
# Host/default namespace
ip -d link show

# Concrete course examples
sudo ip -n info -d link show z-info
sudo ip -n gw   -d link show g-info
Ping says “Network is unreachable”

The source has no matching connected route or default route. Inspect ip route inside the source namespace.

Ping works to gateway, but not to another zone

Check net.ipv4.ip_forward inside gw, destination return route, and the nftables forward chain.

Gateway checks
sudo ip netns exec gw sysctl net.ipv4.ip_forward
sudo ip -n gw route
sudo ip netns exec gw nft list ruleset
curl reports “Connection refused”

Routing reached the destination, but no process is listening at that IP/port, or the service bound only to another address. Check ss -lntp in the destination namespace.

curl times out after firewall rules are applied

This usually means the packet was dropped. Confirm interface names, compare counters before and after the test, and capture on ingress and egress gateway interfaces. For rule-by-rule tracing, first enable meta nftrace set 1 for the selected flow as shown in the failure-injection lab; running nft monitor trace alone is insufficient.

Host nftables looks empty, but traffic is blocked

The active rules are inside gw. Run sudo ip netns exec gw nft list ruleset.

nft command fails with “Operation not permitted”

The command lacks the required privileges, or the environment is an unprivileged container. Use a full VM with root/sudo and kernel namespace support.

Validation and correctness notes

What was checked, and what requires a real privileged VM to verify.

Document checks

  • HTML parsed successfully.
  • JavaScript syntax checked.
  • Interactive controls loaded in a headless Chromium browser.
  • Bridge/router/firewall mode switch, matrix cells, packet timeline, failure selector, tabs, quiz, theme, and download buttons exercised.
  • Internal navigation targets and duplicate IDs checked.
  • Reduced-motion and print behavior included.

Technical checks

  • Namespace, veth, bridge, route, forwarding, nftables, rate-limited logging, packet capture, and temporary nftrace command order reviewed.
  • A lifecycle audit confirmed that namespaces are created before use, veth peers are moved from the namespace that currently owns them, and every later command uses the correct owner namespace.
  • The downloadable setup and cleanup scripts pass bash -n; the generated versions were downloaded through the browser and checked again.
  • Interface names stay within Linux’s 15-byte limit.
  • Examples use documentation address ranges where appropriate and isolated RFC1918 zone ranges for the routed lab.
  • Expected outputs identify values that vary by version or run.
Execution limitation: Browser simulations are educational visualizations; they do not alter the host. Full command execution requires a privileged Linux VM. A restricted container cannot reliably create persistent named namespaces because mount and network capabilities may be blocked.
