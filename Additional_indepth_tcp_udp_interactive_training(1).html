Learning outcome

First, the correct mental model

TCP and UDP both sit above IP. IP tries to deliver packets between hosts; TCP and UDP identify application endpoints with ports and provide different transport services.

TCP is a reliable byte stream

Connection-oriented, ordered, duplicate-suppressed delivery with flow control and congestion control. TCP does not preserve application message boundaries.

UDP is a datagram service

Connectionless, message-oriented and minimal. Each send produces a datagram boundary, but delivery, ordering and duplicate suppression are not guaranteed.

IP can still change the outcome

Packets may be lost, duplicated, reordered, fragmented or delayed. TCP repairs many of these effects; a UDP application must tolerate or repair them itself.

Critical correction: a TCP connection that has truly failed cannot be “resumed” as the same TCP connection. A fresh handshake creates a new connection. Application state may be restored using a token, checkpoint, byte offset, transaction identifier, replay-safe retry or a protocol-specific mechanism.

Animated TCP opening

The three-way handshake, including failure cases

The handshake synchronizes sequence spaces, proves two-way reachability, negotiates options and creates state at both endpoints.

Client: CLOSED
Server: LISTEN
Press Next step. Example initial sequence numbers: client 1000, server 5000.

1. SYN

Client sends SEQ=1000, SYN=1, enters SYN-SENT. SYN consumes one sequence number.

2. SYN + ACK

Server sends SEQ=5000, ACK=1001, enters SYN-RECEIVED. Options are negotiated only if advertised appropriately.

3. ACK

Client sends ACK=5001. Both endpoints reach ESTABLISHED; application data can flow.

Final ACK nuance: if the final ACK is lost, the client may believe the connection is established while the server remains in SYN-RECEIVED. The server retransmits SYN-ACK. The client's response can complete establishment; data carrying a valid ACK may also do so.

Receive window (rwnd)

The receiver advertises available buffer space. A zero window temporarily stops new data; the sender uses persist behavior to probe for a reopened window.

75%

Sender may continue within the advertised window.

Important data-path features

  • Cumulative ACK: ACK N confirms all bytes before N.
  • SACK: reports received non-contiguous byte blocks.
  • Delayed ACK: receiver may briefly delay ACKs to reduce overhead.
  • Nagle: may coalesce small writes; low-latency applications often use TCP_NODELAY.
  • PSH: a sender hint; not an application message delimiter.
Network protection

Flow control is not congestion control

Flow control protects the receiver. Congestion control protects the network path. The sender is effectively limited by the smaller of the receive window and congestion window.

This is a teaching model of classic Reno-style behavior, not a promise of a specific operating system's exact congestion-control implementation.

Core behaviors

  1. Slow start: cwnd grows quickly from a small initial value.
  2. Congestion avoidance: growth becomes roughly linear after the slow-start threshold.
  3. Fast retransmit: repeated duplicate ACKs can signal a missing segment before timeout.
  4. Timeout: indicates more serious uncertainty; classic behavior sharply reduces cwnd and restarts cautiously.
Modern systems may use CUBIC, BBR or other algorithms. The universal lesson is that TCP adapts sending rate based on feedback; UDP applications that send at high rates need their own congestion-aware behavior.

State map

TIME-WAIT normally belongs to the endpoint that performs the active close. It allows delayed duplicates to expire and permits retransmission of the final ACK if the peer retransmits its FIN.

FIN

“I will send no more bytes.” Previously queued data may still arrive. The opposite direction can remain open.

ACK

Acknowledges FIN because FIN consumes one sequence number.

RST

Immediate abort or rejection. Unread buffered data may be discarded; applications see a reset/error.

Half-close

Useful when a client finishes sending a request but still expects the server's response.

Failure and continuity

What happens when the connection breaks?

A cable pull, Wi-Fi roam, NAT timeout, host reboot, address change or prolonged black hole can invalidate the path. TCP may first retransmit because temporary loss is normal. Eventually the application receives an error or times out.

1. DetectRTO, user timeout, socket error, heartbeat or application deadline.
2. ReconnectNew SYN/SYN-ACK/ACK and new TCP state.
3. Re-authenticateReuse a valid session token or establish fresh security context.
4. ReconcileAsk what the server committed; avoid blindly duplicating writes.
5. Resume workContinue from checkpoint, byte range, message ID or transaction state.

Recovery pattern explorer

Do not confuse these mechanisms

  • TCP retransmission: repairs loss while the same connection is still viable.
  • TCP keepalive: optional probes for long-idle connections; not a fast universal failure detector.
  • Application heartbeat: protocol-specific liveness and deadline semantics.
  • TLS resumption: reduces security-handshake work; it does not restore old TCP sequence numbers.
  • Application resumption: restores business or transfer progress.
Exactly-once is not obtained by retrying TCP. If a reply is lost after the server committed an operation, the client cannot infer whether the operation happened. Use idempotency keys, transaction identifiers, deduplication records and a status query.
UDP behavior lab

No handshake does not mean “no design work”

UDP sends independent datagrams immediately. The transport does not establish a connection, retransmit, reorder or pace traffic for you.

SENDER
RECEIVER
Send three datagrams and observe that each is independent.

Strengths

Low protocol overhead, no setup RTT, preserves message boundaries, supports multicast/broadcast patterns, and lets applications control timeliness and repair.

Risks

Loss, duplication, reordering, amplification abuse, fragmentation sensitivity, receiver overload and congestion collapse if the application sends without control.

Reliable UDP?

An application can add sequence numbers, ACKs, retransmission, FEC, pacing and congestion control. At that point it is designing a transport protocol; QUIC is a prominent example built over UDP.

UDP application design checklist

Bound datagram size

Avoid IP fragmentation where practical; discover or conservatively respect path constraints.

Add identity

Message type, version, sequence, timestamp and correlation ID.

Handle duplicates

Deduplicate operations or make messages idempotent.

Control rate

Pacing, backoff and congestion-aware behavior are mandatory for responsible deployment.

Real-world selection

Why real systems choose one, or combine both

HTTPS / REST APIs — TCP

Requests and responses need reliable bytes. HTTP/1.1 and HTTP/2 normally run over TCP; TLS adds security above it.

DNS — commonly UDP, sometimes TCP

Small queries favor UDP. TCP is used for cases such as larger responses, zone transfers and retry/fallback behavior defined by DNS specifications.

Voice/video — often UDP

A late packet may be less useful than a missing packet. Jitter buffers, sequence numbers, loss concealment and adaptive bitrate handle imperfection.

Databases — TCP

Ordered, reliable command and result streams simplify correctness. The application still needs transactions and retry rules.

Online games — often mixed

Position updates may use UDP while login, inventory and purchases use reliable channels or reliable messages.

Vehicle / IoT telemetry — context dependent

Periodic telemetry may use UDP for bounded freshness; firmware updates and commands usually require authenticated, reliable, resumable application protocols.

Advanced operational details

Features commonly encountered in production

MSS, MTU and PMTUD

MSS limits TCP payload size; MTU limits the IP packet carried by a link. Path MTU Discovery tries to avoid fragmentation. A blocked ICMP “packet too big” signal can create a PMTU black hole where handshakes work but larger transfers stall.

Window Scale

The 16-bit TCP window field alone tops out at 65,535. Window Scale, negotiated in SYNs, permits much larger effective receive windows for high bandwidth-delay paths.

Timestamps and PAWS

TCP timestamps improve RTT measurement and help reject old duplicate segments through Protection Against Wrapped Sequence numbers on high-speed paths.

ECN: ECE and CWR

Explicit Congestion Notification can signal congestion without dropping a packet when all relevant endpoints and network devices support it. ECE reports congestion; CWR indicates sender response.

TCP Fast Open

TFO can carry data during connection establishment after cookie-based setup. It reduces latency for suitable applications but early data can have replay-like risks and must be safe to repeat.

SYN backlog and SYN cookies

A listening server holds incomplete handshakes in a queue. Under SYN flood pressure, implementations may use SYN cookies or other defenses, with implementation-dependent trade-offs.

Head-of-line blocking

TCP delivers an ordered byte stream. A missing byte prevents later bytes from being delivered to the application even if later segments arrived. Multiplexed application streams over one TCP connection can therefore interfere with each other.

Offload capture artifacts

Checksum offload, segmentation offload and receive coalescing can make host-side packet captures show apparently bad checksums or unusually large “segments.” Capture on the wire or account for NIC/kernel offload before diagnosing.

“Connected UDP” socket

A program may call connect() on a UDP socket. This sets a default peer and can improve error reporting/filtering, but it creates no UDP handshake and no reliable transport connection.

Multicast, broadcast and ICMP feedback

UDP is commonly used for one-to-many or discovery traffic. Applications must explicitly join multicast groups and control scope. ICMP errors such as Port Unreachable may be reported, but applications cannot treat ICMP delivery as guaranteed.

Security boundary: TCP sequence numbers, checksums and ACKs are not confidentiality, peer authentication or tamper-proof integrity. Use TLS, IPsec, DTLS, QUIC security, or an authenticated application protocol as appropriate.

Lab 3 — Generate and observe an intentional TCP RST

Create rst_server.py:

cat > rst_server.py <<'PY'
import socket, struct
s = socket.socket()
s.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
s.bind(('127.0.0.1', 9090))
s.listen(1)
conn, addr = s.accept()
conn.sendall(b'connected\n')

Lab 7 — Resume an interrupted HTTP download with a new TCP connection

This proves the key distinction: TCP does not resume. The second curl command opens a new connection and uses an HTTP byte-range request to continue the file.

Prepare a range-capable local HTTP server:

sudo apt install -y nginx
sudo systemctl enable --now nginx
sudo dd if=/dev/urandom of=/var/www/html/large.bin bs=1M count=100 status=progress
sha256sum /var/www/html/large.bin | tee /tmp/source.sha256

Start a limited-rate download and interrupt it with Ctrl+C after several seconds:

rm -f resumed.bin
curl --limit-rate 1M -o resumed.bin http://127.0.0.1/large.bin
# Press Ctrl+C after approximately 5–10 seconds.
ls -lh resumed.bin

Resume from the local file size:

curl --limit-rate 1M -C - -o resumed.bin http://127.0.0.1/large.bin
sha256sum resumed.bin
cat /tmp/source.sha256
sudo tail -n 5 /var/log/nginx/access.log
Expected observations: the resumed request normally receives HTTP 206 Partial Content; the final hashes match; packet capture shows a fresh TCP handshake. Resume is safe only when the client verifies it is continuing the same representation, typically using validators such as ETag or Last-Modified in production designs.

Lab 9 — Retry an uncertain API request safely with an idempotency key

Create a local API that commits a transaction before deliberately delaying its first reply:

cat > idempotent_server.py <<'PY'
from http.server import BaseHTTPRequestHandler, HTTPServer
import json, time, uuid

records = {}

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        if self.path != '/charge':
            self.send_error(404)
            return
        key = self.headers.get('Idempotency-Key')
        if not key:
            self.send_error(400, 'Idempotency-Key required')
            return
        replayed = key in records
        if not replayed:
            records[key] = {
                'transaction_id': str(uuid.uuid4()),
                'status': 'committed',
                'amount': 100
            }
            print('COMMITTED', key, records[key], flush=True)
        body = json.dumps({**records[key], 'replayed': replayed}).encode()
        if not replayed:
            time.sleep(2)  # client will time out, but commit already happened
        self.send_response(200)
        self.send_header('Content-Type', 'application/json')
        self.send_header('Content-Length', str(len(body)))
        self.end_headers()
        try:
            self.wfile.write(body)
        except BrokenPipeError:
            pass

HTTPServer(('127.0.0.1', 8088), Handler).serve_forever()
PY
python3 idempotent_server.py

In another terminal, make the first client give up before the reply:

curl --max-time 0.5 -i -X POST \
  -H 'Idempotency-Key: order-1001' \
  http://127.0.0.1:8088/charge

# Retry the same logical request with the same key:
curl -sS -X POST \
  -H 'Idempotency-Key: order-1001' \
  http://127.0.0.1:8088/charge | jq
Expected observations: the first client reports a timeout even though the server logged a commit. The retry returns the same transaction identifier with "replayed": true. Retrying with a different key would create another transaction. Production systems also need durable storage, atomic key enforcement, authentication, request-body matching and expiry rules.

Modern transport comparison

QUIC and HTTP/3: reliable transport implemented over UDP

QUIC uses UDP as its substrate but adds encrypted connection establishment, reliable streams, flow control, loss recovery and congestion control. HTTP/3 maps HTTP semantics onto QUIC streams.

HTTP/2 over one TCP byte stream

TCP delivery
A1B1A2B2A3

HTTP/3 over QUIC streams

QUIC Stream A
A1A2A3
QUIC Stream B
B1B2B3
Inject a loss or simulate a client IP/network change.

What changes—and what does not

  • Independent ordered streams: lost data on one QUIC stream does not create transport-level head-of-line blocking for unrelated streams.
  • Loss still matters: retransmission and shared congestion control can still reduce total sending rate.
  • Integrated security: QUIC integrates TLS 1.3 and encrypts application data plus most transport control information; UDP itself provides none of this.
  • Migration: connection IDs can let an endpoint continue after an address/path change, subject to path validation and policy.
  • Not automatic application recovery: a closed or expired QUIC connection still requires application reconnection and state restoration.
Do not teach “UDP = unreliable application.” UDP only defines the minimal datagram service. A protocol above it can supply reliability, security and congestion control.

Glossary

Fast reference

4-tuple

Source IP, source port, destination IP and destination port. Along with protocol and network namespace/context, it identifies a flow.

ISN

Initial Sequence Number chosen for a TCP direction during connection establishment.

MSS

Maximum Segment Size: maximum TCP payload an endpoint asks the peer to send in one segment.

MTU

Maximum Transmission Unit of a link. MSS is derived to avoid oversized IP packets for a known path/link context.

RTO

Retransmission timeout calculated from measured timing and bounded rules.

RTT

Round-trip time for traffic and acknowledgment feedback.

SACK

Selective Acknowledgment: reports received byte blocks beyond a gap.

rwnd / cwnd

Receiver-advertised flow-control window / sender congestion-control window.

TIME-WAIT

Post-close state that protects against delayed duplicates and supports reliable completion of closing.

Idempotent

Repeating the same logical request has the same intended effect as performing it once.
