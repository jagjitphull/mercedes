Real-world framing

Connected-vehicle telemetry gateway

The situation

A telemetry daemon accepts health requests from a trusted diagnostics workstation. It must serve public status files, but it must not read private keys, modify system configuration, open raw sockets, or accept traffic from arbitrary networks.

The same model applies to web servers, API gateways, DNS services, database listeners, monitoring agents, and update daemons.

Control ownership

nftables answers: “Which packets may reach port 8080?”

AppArmor answers: “Once the daemon runs, which files, capabilities, processes, and socket operations may it use?”

DAC still applies underneath: Unix owner/group/mode bits remain relevant, but MAC can impose an additional restriction.

Concept 2

AppArmor profile structure

#include <tunables/global>
profile aa-lab-server /opt/aa-lab/bin/aa-demo-busybox {
  #include <abstractions/base>
  /opt/aa-lab/bin/aa-demo-busybox mr,
  /srv/aa-lab/www/ r,
  /srv/aa-lab/www/** r,
  /etc/mime.types r,
  network inet stream,
}

Click a profile line

The explanation will appear here. Notice the allow-list model: absent permissions are denied when enforcing.

Common permissions: r read, w write, m executable mapping, ix inherit current profile on exec, Px transition to another profile.

Path-oriented

AppArmor commonly expresses file policy using path patterns. Renames, bind mounts, aliases, deleted paths, and namespaces deserve deliberate testing.

Least privilege

Grant the smallest file, capability, network, signal, DBus, and execution permissions needed for normal operation.

Order-independent

Rules in a profile are declarative; their order does not create firewall-like first-match behavior. Permissions accumulate.

Concept 3

Complain and enforce mode

Observe without blocking most policy violations

Complain mode is useful during profile development. Potential violations are logged, but the attempted access is normally allowed. This is not a production protection mode.

Typical log direction: an event can appear as apparmor="ALLOWED" because policy would have denied it under enforcement.

Block and log policy violations

Enforce mode applies the profile. Missing permissions cause the kernel to reject the operation and record a denial event.

Typical log direction: apparmor="DENIED" operation="open" ... requested_mask="r" denied_mask="r".

Concept 4

Network restrictions and daemon confinement

Important boundary: AppArmor network rules govern socket operations available to the process. nftables evaluates packets in the network stack. The core lab intentionally uses network inet stream, and delegates source IP and destination-port filtering to nftables. Fine-grained AppArmor IP/port syntax exists in newer policy ABIs, but support must be verified on the target kernel and userspace.

What to confine

Executable path, web/config directories, log path, required libraries, DNS files, capabilities, socket families/types, child execution, signals, and IPC.

What to observe

Service logs, AppArmor audit events, listening sockets, process profile label, nftables counters, and the application’s normal transaction tests.

What not to do

Do not blindly approve every aa-logprof suggestion. A noisy application can train an over-permissive profile.

Control boundaries

Who owns which security decision?

RequirementAppArmornftablesPractical interpretation
Restrict files a daemon reads or writesYesNoUse narrow path rules and validate both allowed and denied resources.
Restrict execution transitions and Linux capabilitiesYesNoConstrain child execution and privileged kernel operations in the profile.
Filter source/destination addresses and portsVersion-dependent / limitedYesTeach and deploy nftables for portable packet-level address and port policy.
Track established and related connectionsNoYesUse connection tracking expressions such as ct state.
Rate-limit or count packetsNoYesUse nftables counters, limits, sets, and logs.
Stop a compromised daemon reading SSH keysYesNoThe firewall cannot see local file reads.
Stop an unauthorized remote client before the daemonNot the main controlYesDrop the packet at the input hook and inspect rule counters.
Memory rule: nftables decides whether the conversation may reach the process; AppArmor decides what the process may do after it runs.
Production maintainability

Abstractions, tunables, local overrides, and systemd

🧱 Abstractions

Reusable policy fragments under /etc/apparmor.d/abstractions/. Prefer a reviewed abstraction over repeatedly copying common runtime rules.

🔧 Tunables

Reusable variables and site settings under /etc/apparmor.d/tunables/, such as home-directory patterns and aliases.

🧩 Local overrides

Site-specific additions commonly stored under /etc/apparmor.d/local/ and explicitly included by the parent profile. This reduces package-upgrade conflicts.

#include <tunables/global>

profile telemetry-service /usr/local/bin/telemetry-service {
  #include <abstractions/base>
  #include <abstractions/nameservice>
  #include if exists <local/usr.local.bin.telemetry-service>

  /etc/telemetry/config.yaml r,
  /var/lib/telemetry/** rw,
  /var/log/telemetry/*.log w,
  network inet stream,
  capability net_bind_service,
  /usr/bin/logger ix,
}

Create the trusted and unauthorized client namespaces

The commands remove only old objects with the lab-specific names, making the setup safe to repeat after an interrupted attempt.

cat > /tmp/aa-netns-setup.sh <<'EOF'
#!/usr/bin/env bash
set -Eeuo pipefail

TRUST_NS='aa-client'
UNTRUST_NS='aa-untrusted'
TRUST_HOST_IF='veth-aa-server'
TRUST_NS_IF='veth-aa-client'
UNTRUST_HOST_IF='veth-aa-u-host'
UNTRUST_NS_IF='veth-aa-u-cli'

cleanup_lab_links() {
  ip netns del "$TRUST_NS" 2>/dev/null || true
  ip netns del "$UNTRUST_NS" 2>/dev/null || true
  ip link del "$TRUST_HOST_IF" 2>/dev/null || true
  ip link del "$UNTRUST_HOST_IF" 2>/dev/null || true
}

for ifname in "$TRUST_HOST_IF" "$TRUST_NS_IF" "$UNTRUST_HOST_IF" "$UNTRUST_NS_IF"; do
  if (( ${#ifname} > 15 )); then
    echo "[FAIL] Interface name '$ifname' is longer than Linux permits (15 characters)." >&2
    exit 1
  fi
done

# Make reruns predictable after a partial or failed attempt.
cleanup_lab_links
trap 'rc=$?; echo "[FAIL] Namespace setup stopped at line $LINENO (exit $rc). Cleaning lab links." >&2; cleanup_lab_links; exit $rc' ERR

# Trusted client: root namespace 10.200.0.1 <-> aa-client 10.200.0.2
ip netns add "$TRUST_NS"
ip link add "$TRUST_HOST_IF" type veth peer name "$TRUST_NS_IF"
ip link set "$TRUST_NS_IF" netns "$TRUST_NS"
ip address add 10.200.0.1/24 dev "$TRUST_HOST_IF"
ip link set "$TRUST_HOST_IF" up
ip netns exec "$TRUST_NS" ip address add 10.200.0.2/24 dev "$TRUST_NS_IF"
ip netns exec "$TRUST_NS" ip link set lo up
ip netns exec "$TRUST_NS" ip link set "$TRUST_NS_IF" up

# Unauthorized client: root namespace 10.201.0.1 <-> aa-untrusted 10.201.0.2
ip netns add "$UNTRUST_NS"
ip link add "$UNTRUST_HOST_IF" type veth peer name "$UNTRUST_NS_IF"
ip link set "$UNTRUST_NS_IF" netns "$UNTRUST_NS"
ip address add 10.201.0.1/24 dev "$UNTRUST_HOST_IF"
ip link set "$UNTRUST_HOST_IF" up
ip netns exec "$UNTRUST_NS" ip address add 10.201.0.2/24 dev "$UNTRUST_NS_IF"
ip netns exec "$UNTRUST_NS" ip link set lo up
ip netns exec "$UNTRUST_NS" ip link set "$UNTRUST_NS_IF" up

trap - ERR
echo '[PASS] Both namespace/veth paths were created successfully.'
EOF

chmod +x /tmp/aa-netns-setup.sh
sudo /tmp/aa-netns-setup.sh
Why no bridge or IP forwarding? Each client namespace is directly connected to an IP address owned by the root namespace. The clients are testing services on the host itself, so packets enter the host’s nftables input hook; they are not being routed through it.

Lab 2 — Create and syntax-check the AppArmor profile
30 minRoot namespace
cat <<'EOF' | sudo tee /etc/apparmor.d/aa-lab-server
#include <tunables/global>

Lab 3 — Compare complain and enforce mode
30 minRoot namespace

A. Complain mode

sudo aa-complain /opt/aa-lab/bin/aa-demo-busybox
sudo aa-status | grep -A5 'profiles are in complain mode'

sudo /opt/aa-lab/bin/aa-demo-busybox cat /root/aa-lab-secret.txt

B. Enforce mode

sudo aa-enforce /opt/aa-lab/bin/aa-demo-busybox
sudo /opt/aa-lab/bin/aa-demo-busybox cat /root/aa-lab-secret.txt; echo "exit=$?"

Expected: BusyBox reports Permission denied, returns a nonzero exit status, and the kernel log contains apparmor="DENIED" for an open/read operation on the fake secret.
Log interpretation: profile= identifies the confined domain; name= identifies the resource; requested_mask= is what the process asked for; denied_mask= is what policy blocked.
Lab 4 — Run the confined network daemon

Lab 6 — Add nftables without disturbing the host ruleset
40 minSingle VM + namespacesConsole recommended

Create a dedicated table. The chain’s default policy is accept, so only TCP port 8080 is affected by the explicit final drop rule. The trusted namespace source 10.200.0.2 is accepted; the unauthorized namespace source 10.201.0.2 reaches the final drop rule.

# Do not continue unless both namespace paths and the daemon work before filtering.
sudo ip netns exec aa-client ip route get 10.200.0.1
sudo ip netns exec aa-untrusted ip route get 10.201.0.1
sudo systemctl is-active aa-lab-http.service
sudo ip netns exec aa-client curl -fsS --max-time 3 http://10.200.0.1:8080/ >/dev/null && echo '[PASS] trusted path works before filtering'
sudo ip netns exec aa-untrusted curl -fsS --max-time 3 http://10.201.0.1:8080/ >/dev/null && echo '[PASS] unauthorized path works before filtering'
Expected: both route lookups resolve through their namespace-side veth interfaces, the service reports active, and both pre-filter curl tests print PASS. If not, return to Labs 0 or 4 instead of troubleshooting nftables.
cat <<'EOF' | sudo tee /tmp/aa-lab.nft
table inet aa_lab {
  chain input {
    type filter hook input priority 10; policy accept;

    iifname "lo" tcp dport 8080 counter accept comment "allow local loopback test"
    ip saddr 10.200.0.2 tcp dport 8080 ct state new,established counter accept comment "allow trusted namespace"
    tcp dport 8080 counter drop comment "drop all other clients to lab service"
  }
}
EOF

# A previous lab table can make a repeat syntax check report 'File exists'.
# Delete only this dedicated training table before validating and loading it.
sudo nft list table inet aa_lab >/dev/null 2>&1 && sudo nft delete table inet aa_lab || true

sudo nft -c -f /tmp/aa-lab.nft
printf 'nft syntax exit=%s\n' "$?"
sudo nft -f /tmp/aa-lab.nft
sudo nft -a list table inet aa_lab
Expected: syntax exit code 0. The listed table contains loopback accept, trusted-client accept, and final port-8080 drop rules with counters.

Trusted namespace: should succeed

sudo ip netns exec aa-client \
  curl -i --max-time 3 http://10.200.0.1:8080/
Expected: HTTP 200 because the packet source is 10.200.0.2, matching CLIENT_IP.

Unauthorized namespace: should fail

sudo ip netns exec aa-untrusted \
  curl -v --max-time 3 http://10.201.0.1:8080/ || true

sudo nft list chain inet aa_lab input
Expected: curl times out or fails without receiving the page, and the final TCP-port-8080 drop counter increases. The service remains running; packet policy—not daemon failure—causes the block.
Existing firewall note: Ubuntu may also be managed by UFW, firewalld, container software, or another nftables manager. Independent base chains can interact. Always inspect nft list ruleset and test through a console-safe path.

Optional: trace packets correctly with nft monitor trace

The monitor is silent unless a rule first sets meta nftrace set 1. Use this temporary trace table in one terminal, generate one request in another terminal, then remove the trace table.

# Safe to rerun: remove only the temporary trace table if it exists.
sudo nft list table inet aa_trace >/dev/null 2>&1 && sudo nft delete table inet aa_trace || true

cat <<'EOF' | sudo nft -f -
table inet aa_trace {
  chain prerouting {
    type filter hook prerouting priority -301; policy accept;
    tcp dport 8080 meta nftrace set 1
  }
}
EOF

# Capture traces for a few seconds in the background.
sudo sh -c 'timeout 5 nft monitor trace > /tmp/aa-nft-trace.log 2>&1' &
TRACE_PID=$!
sleep 1
sudo ip netns exec aa-client curl -sS --max-time 3 http://10.200.0.1:8080/ >/dev/null
wait "$TRACE_PID" || true

sudo sed -n '1,80p' /tmp/aa-nft-trace.log
sudo nft delete table inet aa_trace
sudo rm -f /tmp/aa-nft-trace.log
Expected: trace records identify the packet path and the matching aa_lab accept rule. Running nft monitor trace without the temporary nftrace rule produces no packet trace output.

Lab 8 — Intentional misconfiguration challenge
30–40 minBreak/fixDo not use on production hosts

The trainer selects one fault. Trainees must identify the failing layer, collect evidence, fix only that layer, and prove secure recovery.

Fault cards

  1. Change the profile attachment to a nonexistent executable.
  2. Leave the profile in complain mode and claim it is enforcing.
  3. Remove the web-root read rule.
  4. Change the nftables trusted source to the wrong IP.
  5. Stop the service while leaving both security controls intact.
  6. Move the executable to /opt/aa-lab/bin/v2/ without updating the attachment.

Required evidence

  1. Observed symptom and timestamp
  2. Process/service state
  3. Current AppArmor label and mode
  4. Relevant denial or absence of denial
  5. nftables counter evidence
  6. Smallest corrective change
  7. Positive and negative retest
Forbidden shortcuts: Do not disable AppArmor, do not permanently leave complain mode, and do not run nft flush ruleset. Those actions remove evidence and can create a larger outage.
Pass condition: the normal page is reachable only from the trusted client; secret reads and unauthorized clients remain blocked; the profile is enforcing.
Lab 9 — AppArmor allows the socket; nftables blocks the client
20 minNamespace proof

Keep the AppArmor profile enforcing with network inet stream, and keep the Lab 6 nftables table loaded. The daemon may create its TCP socket, while nftables independently rejects the unauthorized namespace.

if ! sudo nft list table inet aa_lab >/dev/null 2>&1; then
  echo '[FAIL] nftables table inet aa_lab is absent. Complete or rerun Lab 6 first.'
else
  sudo aa-status | grep -E 'aa-lab-server|enforce'
  PID="$(sudo systemctl show -p MainPID --value aa-lab-http.service)"
  sudo cat "/proc/$PID/attr/current"
  sudo ss -lntp | grep ':8080'
  sudo nft list chain inet aa_lab input
fi
Expected: AppArmor shows aa-lab-server (enforce), and the daemon is listening on 0.0.0.0:8080.

Generate an unauthorized request and inspect the firewall counter:

sudo ip netns exec aa-untrusted \
  curl -v --max-time 3 http://10.201.0.1:8080/ || true

sudo nft list chain inet aa_lab input
Expected: curl times out or fails, while the final drop counter increases. This proves AppArmor allowed the daemon’s socket operation and nftables blocked the packet by network policy.

Confirm the trusted path remains available:

sudo ip netns exec aa-client \
  curl -i --max-time 3 http://10.200.0.1:8080/
Expected: HTTP 200 from the trusted namespace.

Lab 11 — Application upgrade changes the executable path
25 minLifecycle scenario

Copy the daemon to a versioned path. Because AppArmor attachment is path-oriented, the old profile does not automatically attach to the new executable.

sudo install -d -m 0755 /opt/aa-lab/bin/v2
sudo install -m 0755 /opt/aa-lab/bin/aa-demo-busybox /opt/aa-lab/bin/v2/aa-demo-busybox
sudo sh -c '/opt/aa-lab/bin/v2/aa-demo-busybox sleep 20 & echo $! >/run/aa-lab-v2.pid'
PID="$(sudo cat /run/aa-lab-v2.pid)"
echo "v2 PID=$PID"
sudo cat "/proc/$PID/attr/current"
sudo kill "$PID" 2>/dev/null || true
sudo rm -f /run/aa-lab-v2.pid
Expected before update: the v2 process is normally unconfined because the profile attaches to the original exact path.

Create a separate profile for the new path rather than silently widening the original attachment:

sudo sed   -e 's/profile aa-lab-server /profile aa-lab-server-v2 /'   -e 's#/opt/aa-lab/bin/aa-demo-busybox#/opt/aa-lab/bin/v2/aa-demo-busybox#g'   /etc/apparmor.d/aa-lab-server | sudo tee /etc/apparmor.d/aa-lab-server-v2
sudo apparmor_parser -Q /etc/apparmor.d/aa-lab-server-v2
sudo apparmor_parser -r /etc/apparmor.d/aa-lab-server-v2
sudo aa-status | grep 'aa-lab-server-v2'
sudo sh -c '/opt/aa-lab/bin/v2/aa-demo-busybox sleep 20 & echo $! >/run/aa-lab-v2.pid'
PID="$(sudo cat /run/aa-lab-v2.pid)"
sudo cat "/proc/$PID/attr/current"
sudo kill "$PID" 2>/dev/null || true
sudo rm -f /run/aa-lab-v2.pid
Production lesson: executable-path changes are security-significant release events. Include profile attachment tests in deployment validation.

Remove the temporary v2 profile before the general cleanup:

sudo apparmor_parser -R /etc/apparmor.d/aa-lab-server-v2 2>/dev/null || true
sudo rm -f /etc/apparmor.d/aa-lab-server-v2
sudo rm -rf /opt/aa-lab/bin/v2
