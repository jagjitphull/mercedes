Mental model 2

Ethernet, IP, TCP, UDP and ICMP

These protocols cooperate. Ethernet reaches the next local device, IP reaches the end network, transport identifies the conversation, and ICMP reports network conditions.

Ethernet: delivery on the local link

Ethernet frames carry source and destination MAC addresses. A switch learns which source MAC appears on which port, then forwards known unicast frames toward the learned destination port. Broadcasts and unknown unicasts may be flooded within the VLAN.

Analogy: An office mailroom delivers envelopes to desks on the same floor. The desk label is the MAC address; the floor is the VLAN.

Typical operational clue: Correct IP configuration cannot compensate for the wrong VLAN, a down link, or unresolved ARP/neighbor information.

IP: best-effort delivery across networks

IP provides logical addressing and routing. Routers examine the destination address and choose a next hop using the most specific matching route. IP itself does not guarantee delivery, order, uniqueness or application success.

Analogy: A postal address gets a parcel across cities. Each sorting center only needs the next direction, not the full physical path.

IPv4 essentials: source, destination, TTL, protocol number and fragmentation-related fields. IPv6 essentials: a larger address space, hop limit and extension-header model; routers do not fragment transit packets.

TCP: reliable ordered byte stream

TCP establishes state, numbers bytes, acknowledges delivery, retransmits loss, controls flow and reacts to congestion. Applications see a byte stream—not preserved message boundaries.

Client: SYN→Server: SYN-ACK→Client: ACK→ESTABLISHED

Analogy: A courier obtains confirmation, numbers multi-box shipments and resends missing boxes.

UDP: independent datagrams with low protocol overhead

UDP sends discrete datagrams without a transport-layer handshake, retransmission or ordering. The application may add reliability when needed. It is common for DNS, telemetry, real-time media and protocols such as QUIC.

Analogy: A live announcer keeps speaking even if one listener misses a sentence. Timeliness can matter more than retransmitting old audio.

Do not say “UDP is always faster.” It has less built-in machinery, but application design, congestion behavior, packet loss and path conditions determine performance.

ICMP: control and error reporting for IP

ICMP reports conditions such as unreachable destinations, TTL expiry and packet-too-big. The familiar ping tool uses Echo Request and Echo Reply, but ICMP is much broader than ping.

Analogy: Road signs and delivery-failure notices. Blocking all notices can hide broken routes and interfere with path MTU discovery.

ping -c 3 1.1.1.1
tracepath 1.1.1.1
sudo tcpdump -ni any 'icmp or icmp6'

Current fields and scope

How this appears in a real packet capture

A capture on the client-facing link and another on the server-facing link normally show the same source/destination IP addresses and transport ports. The Ethernet source/destination MAC addresses differ because each link has a different local sender and next hop. The second capture also shows a TTL reduced by one. With DNAT/SNAT, the relevant IP address or port also changes.

PDU names trainees should use
  • Application data: the message, such as an HTTP request or DNS query.
  • TCP segment / UDP datagram: transport header plus application data.
  • IP packet: IP header plus the transport unit.
  • Ethernet frame: Ethernet header and trailer around the IP packet.
  • Bits/signals: the encoded representation transmitted over copper, fibre or radio.
Boundaries and address plans

VLANs and subnetting

VLAN: one switch, multiple Layer-2 broadcast domains

A VLAN separates Ethernet forwarding domains. Access ports carry one VLAN untagged for endpoints. Trunks commonly carry multiple VLANs with IEEE 802.1Q tags between switches, routers, hypervisors or firewalls.

Analogy: People wear colored event wristbands in the same building. Staff forward them only into rooms assigned to that color.

Boundary rule: Hosts in different VLANs need a Layer-3 device to communicate, and that routed boundary is where policy is commonly enforced.

Subnetting: divide an IP space into routing domains

A prefix such as 192.168.10.0/24 says the first 24 bits identify the network. Longer prefixes mean smaller networks; shorter prefixes mean larger networks.

11000000101010000000101000000000

/24: 24 network bits + 8 host bits. Conventionally 254 usable IPv4 host addresses; /31 and /32 are special cases.

Choosing the next hop

Routing and gateways

A host first determines whether the destination is on-link. If not, it sends the frame to a next-hop router—usually its default gateway—while the IP destination remains the final endpoint.

Route selection: longest prefix match

Given routes for 10.0.0.0/8, 10.20.0.0/16, and 10.20.30.0/24, a packet for 10.20.30.55 uses the /24 route because it is the most specific.

Destination IP→Policy rules→Route table lookup→Next hop + egress→Neighbor resolution
ip address show
ip route show
ip route get 10.20.30.55
ip neigh show

Gateway analogy

Analogy: Your apartment number works inside the complex. To reach another city, the parcel goes through the complex exit gate. The gateway is not “the internet”; it is simply the next router.

Common failure patterns

  • Wrong mask: host thinks a remote address is local and ARPs for it.
  • Missing default: local subnet works, remote networks fail.
  • Asymmetric routing: return traffic takes a different path; stateful devices may drop it.
  • Neighbor failure: route exists, but next-hop MAC resolution fails.

Policy enforcement

Stateful vs stateless firewalling

Both approaches inspect packet fields. The difference is whether the decision can use remembered connection context.

Stateless

Each packet is evaluated independently against fields such as source, destination, protocol, ports and interface.

  • Simple and predictable per packet
  • Useful for coarse filtering and some high-speed paths
  • Return traffic needs explicit reverse-direction rules
  • Cannot distinguish a legitimate reply from an unsolicited packet by state alone

Analogy: A guard checks every visitor’s visible details but keeps no visitor log.

Stateful

The firewall uses connection tracking metadata such as new, established, related and invalid.

  • Return traffic can be permitted with one state rule
  • Supports NAT mappings and richer policy
  • Consumes memory and requires state-table capacity planning
  • Asymmetric paths can break assumptions

Analogy: The guard records visitors and recognizes their authorized return path.

Operational reality: Stateful does not mean “secure by default.” Rule direction, default policy, application exposure, state exhaustion, logging and change control still matter.
Address translation

NAT, SNAT, DNAT and MASQUERADE

NAT rewrites address and sometimes port fields. It solves addressing and publishing problems; it is not a substitute for an explicit filtering policy.

SNAT

Changes the source address, usually as traffic leaves a routed boundary. A fixed translated address is common.

Analogy: Employees send mail through one corporate return address.

Common hook: postrouting

DNAT

Changes the destination address or port, commonly to publish an internal service behind a public or gateway address.

Analogy: Reception redirects the company’s main number to the correct internal extension.

Common hook: prerouting

MASQUERADE

A dynamic-address form of source NAT that uses the current egress-interface address. Convenient for changing addresses; fixed SNAT is preferred when the address is stable.

Analogy: The return address automatically changes to whichever branch office dispatches the parcel.

Remembering flows

Conntrack: the state table behind stateful filtering and NAT

Linux Netfilter associates packets with tracked flows. For TCP, flags and direction help determine state; for UDP and ICMP, tracking uses protocol-specific tuples and timeouts even though UDP itself has no connection handshake.

Core state labels

NEW

Packet starts or belongs to a flow not yet seen bidirectionally.

ESTABLISHED

Traffic is associated with a flow that has seen valid communication context.

RELATED

A distinct flow is associated with an existing one, such as certain control/error traffic.

INVALID

Packet cannot be associated reliably with a valid tracked flow.

Linux Netfilter path

Firewall packet decision flow

The route decision determines which hook path is relevant. Rules are attached to base chains at hooks; table and chain names are administrator-defined.

Filtering chains

  • input: traffic delivered to a local process.
  • forward: traffic routed through the host.
  • output: traffic created by a local process.

NAT placement

  • prerouting: destination translation before route selection.
  • output: destination translation for locally generated traffic when required.
  • postrouting: source translation after egress selection.
nftables design note: Unlike legacy fixed table/chain names, nftables lets you create named tables and chains. A chain participates in packet processing only when configured as a base chain with a hook, type and priority.

Lab 2 · Build a routed three-node topology

35 minNamespaces
🧱

Outcome: Create client → firewall/router → server, configure addressing and prove routing before filtering.

# Create namespaces
sudo ip netns add client
sudo ip netns add fw
sudo ip netns add server

# Create two point-to-point Ethernet links
sudo ip link add veth-client type veth peer name veth-fw-c
sudo ip link add veth-server type veth peer name veth-fw-s
sudo ip link set veth-client netns client
sudo ip link set veth-fw-c netns fw
sudo ip link set veth-server netns server
sudo ip link set veth-fw-s netns fw

# Configure client
sudo ip -n client link set lo up
sudo ip -n client link set veth-client up
sudo ip -n client addr add 10.10.1.10/24 dev veth-client
sudo ip -n client route add default via 10.10.1.1

# Configure firewall/router
sudo ip -n fw link set lo up
sudo ip -n fw link set veth-fw-c up
sudo ip -n fw link set veth-fw-s up
sudo ip -n fw addr add 10.10.1.1/24 dev veth-fw-c
sudo ip -n fw addr add 10.10.2.1/24 dev veth-fw-s
sudo ip netns exec fw sysctl -w net.ipv4.ip_forward=1

# Configure server
sudo ip -n server link set lo up
sudo ip -n server link set veth-server up
sudo ip -n server addr add 10.10.2.20/24 dev veth-server
sudo ip -n server route add default via 10.10.2.1

# Verify
sudo ip netns exec client ping -c 2 10.10.1.1
sudo ip netns exec client ping -c 2 10.10.2.20
sudo ip netns exec client ip route get 10.10.2.20

  • The firewall-side address 10.10.1.1 usually replies with ttl=64 because it is local to the router namespace.
  • The server reply commonly arrives with ttl=63 because the firewall routed it across one hop.

The client sees 10.10.2.20 as remote, so it sends an Ethernet frame to gateway 10.10.1.1. Namespace fw performs a route lookup and forwards it to 10.10.2.0/24. The server returns through 10.10.2.1.

Lab 3 · Compare stateless and stateful forwarding

45 minnftables
🛡️

Outcome: See why a one-way stateless rule breaks replies, then solve it with conntrack state.

Start a web server in a separate terminal and leave this terminal running through Labs 3, 4 and 5:

# Terminal S — keep this process running
sudo ip netns exec server python3 -m http.server 8080 --bind 10.10.2.20

Expected output — server terminal

Serving HTTP on 10.10.2.20 port 8080 (http://10.10.2.20:8080/) ...

The command intentionally remains in the foreground. During each successful curl, this terminal should also log a request similar to 10.10.1.10 - - [date/time] "GET / HTTP/1.1" 200 -.

Python wording and the request timestamp can differ slightly by version.

Listener check: In another terminal, confirm that the service is listening before continuing:
sudo ip netns exec server ss -lntp | grep ':8080'
If no line is returned, the web server is not running. Restart Terminal S. If Python reports Address already in use, an existing server is already listening.

Install a deliberately incomplete stateless policy:

sudo ip netns exec fw nft flush ruleset
sudo ip netns exec fw nft -f - <<'NFT'
table inet labfw {
  chain forward {
    type filter hook forward priority 0; policy drop;
    iifname "veth-fw-c" oifname "veth-fw-s" \
      ip saddr 10.10.1.0/24 ip daddr 10.10.2.20 \
      tcp dport 8080 accept
  }
}
NFT

sudo ip netns exec client curl --noproxy '*' -sS --max-time 3 \
  -o /dev/null -w 'HTTP status: %{http_code}\n' \
  http://10.10.2.20:8080/

Expected output — incomplete stateless policy

curl: (28) Operation timed out after 3000 milliseconds with 0 bytes received
HTTP status: 000

The SYN reaches the server because the forward rule allows client → server TCP/8080. The SYN-ACK or later reply is dropped by the default policy because no reverse-direction rule exists.

Acceptable variations: the timeout may report approximately 3000 ms, or curl may say “Connection timed out.” The required result is failure before receiving HTTP data.

The request enters, but the reply has no matching reverse rule. Replace it with a stateful policy:

sudo ip netns exec fw nft -f - <<'NFT'
flush ruleset
table inet labfw {
  chain forward {
    type filter hook forward priority 0; policy drop;
    ct state invalid drop
    ct state established,related accept
    iifname "veth-fw-c" oifname "veth-fw-s" \
      ip saddr 10.10.1.0/24 ip daddr 10.10.2.20 \
      tcp dport 8080 ct state new accept
  }
}
NFT
sudo ip netns exec client curl --noproxy '*' -sS \
  -o /dev/null -w 'HTTP status: %{http_code}\n' \
  http://10.10.2.20:8080/
sudo ip netns exec fw nft list ruleset
sudo ip netns exec fw conntrack -L -p tcp 2>/dev/null

Expected output — stateful policy succeeds

$ sudo ip netns exec server ss -lntp | grep ':8080'
LISTEN 0 5 10.10.2.20:8080 0.0.0:* users:(("python3",pid=2148,fd=3))

$ sudo ip netns exec client curl ...
HTTP status: 200

$ sudo ip netns exec fw nft list ruleset
table inet labfw {
    chain forward {
        type filter hook forward priority filter; policy drop;
        ct state invalid drop
        ct state established,related accept
        iifname "veth-fw-c" oifname "veth-fw-s" ip saddr 10.10.1.0/24 ip daddr 10.10.2.20 tcp dport 8080 ct state new accept
    }
}

$ sudo ip netns exec fw conntrack -L -p tcp
tcp 6 1XX TIME_WAIT src=10.10.1.10 dst=10.10.2.20 sport=49XXX dport=8080 \
    src=10.10.2.20 dst=10.10.1.10 sport=8080 dport=49XXX [ASSURED] ...
  • HTTP status: 200 proves request and reply both crossed the firewall.
  • The ruleset must show policy drop, an established,related acceptance rule and a narrowly scoped new rule.
  • Conntrack should show both directions of the same flow. The state may be ESTABLISHED, FIN_WAIT or TIME_WAIT depending on when it is inspected.

Acceptable variations: Python PID, client source port, conntrack timeout, TCP state, rule formatting and handle numbers differ.

  • The DNAT rule counter must be at least 1.

Acceptable variations: HTTP version, server header, source port, state, timeout, packet and byte counters. Treat all counter values as examples; only “non-zero” matters.

Why does the forward rule match 10.10.2.20:8080?

The incoming packet first traverses the prerouting hook. DNAT rewrites 10.10.1.1:8088 to 10.10.2.20:8080 before the route decision. The forwarded packet therefore reaches the forward chain with the translated destination. Conntrack stores both the original and translated tuples so the reply can be reversed correctly.

Fast diagnosis when curl still fails
  1. No server listener: sudo ip netns exec server ss -lntp | grep ':8080' returns nothing. Restart the Python server.
  2. DNAT counter remains zero: the packet did not match prerouting. Recheck iifname, destination address and destination port.
  3. DNAT counter increases but forward counter remains zero: inspect the translated route and rule fields with nft -a list ruleset and ip route get 10.10.2.20.
  4. Both counters increase but curl fails: capture on veth-fw-s and inspect the server listener and return route.
  5. Corporate proxy variables interfere: retain --noproxy '*' in every curl command.
  6. Clear only this lab's stale test entries if required: sudo ip netns exec fw conntrack -D -p tcp --dport 8088 2>/dev/null || true, then retry.

Trainer answer: Why can ping work while the application fails?

ICMP Echo and the application’s transport flow are separate protocols and policy matches. Routing may work while a TCP port is filtered, no process is listening, TLS fails, or the application rejects the request.

Trainer answer: Why can a firewall see ESTABLISHED before the application responds?

Conntrack state represents the network flow’s observed packet context, not application-level success. A TCP handshake can be established even if the later HTTP request receives an error.

Trainer answer: Does a VLAN provide security?

It provides segmentation, not complete security. Inter-VLAN routing policy, switch protections, endpoint controls, management-plane security and monitoring determine the effective security boundary.
