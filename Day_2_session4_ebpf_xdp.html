Learning outcomes and lab contract

By the end, trainees can

  • Define eBPF without calling it a firewall, protocol or replacement kernel.
  • Explain the verifier, maps, helpers, program types and attachment.
  • Choose XDP, TC, cgroup or socket hooks for a stated requirement.
  • Inspect loaded programs and maps with bpftool.
  • Trace live kernel events using bpftrace.
  • Compile and attach small XDP, TC and cgroup programs safely.
  • Collect evidence, verify behavior, roll back and clean up.

Lab baseline

Primary tested path: Ubuntu 24.04-class VM, x86_64, modern Linux kernel, root/sudo, cgroup v2. Commands include capability checks so trainees fail safely on incompatible VMs.

Virtual-machine reality: XDP native-driver mode depends on the virtual NIC and driver. The lab deliberately uses xdpgeneric for portability. It proves logic and attachment, but it is not a native-XDP performance benchmark.

Recommended: 2 vCPU, 4 GB RAM, 20 GB free disk, internet access for package installation, and a snapshot before the labs.

Big picture

The simplest accurate mental model

🧠
eBPF

A verified program runtime inside the Linux kernel.

It lets approved programs run at supported kernel events without writing a traditional kernel module.

⚡
XDP

A very early ingress packet-processing hook.

It can pass, drop, transmit or redirect packets before the normal network stack does most work.

🚦
TC

Traffic-control hooks around the network stack.

eBPF classifiers/actions can inspect and modify ingress or egress traffic using an skb context.

📦
cgroup

A hierarchy that groups processes and workloads.

eBPF programs can attach to cgroup events to apply policy to every process in that workload group.

Analogy: eBPF is the programmable security officer. XDP is the gate before visitors enter the building, TC is the traffic desk in the lobby and exit, cgroup hooks apply rules to a department, and socket filters protect or observe a specific communication endpoint.

Do not confuse these

Incorrect shortcutAccurate correction
“eBPF is a firewall.”eBPF is a mechanism. A firewall is one application built with it.
“XDP bypasses the kernel.”XDP runs in the kernel. It bypasses much of the normal networking stack for selected packets.
“cgroup is an eBPF hook.”cgroup is a workload hierarchy. Linux exposes several BPF program types and attach points associated with cgroups.
“The verifier proves the program is bug-free.”It checks safety properties and program constraints. It does not prove business logic, policy intent or operational correctness.
“TC is obsolete because XDP is faster.”TC sees richer skb context, supports ingress and egress, and may be the correct hook even when XDP is available.
Concept 1

What is eBPF, and what does it do?

Definition: eBPF is a Linux kernel facility for loading programs into a constrained instruction set, verifying them, and attaching them to supported kernel events. Programs can inspect context, call allowed helper functions, update maps, emit events, and—depending on program type—allow, deny, modify, redirect or measure an operation.

What eBPF programs commonly do

Networking

DDoS filtering, service load balancing, traffic accounting, tunnelling, policy enforcement and packet redirection.

Observability

Trace syscalls, functions, latency, block I/O, TCP behavior and application events with lower friction than custom kernel modules.

Security

Observe or enforce selected process, file, socket and workload behaviors through appropriate program types and hooks.

Safety and state

Verifier and maps

The verifier

The kernel analyzes a program before accepting it. It tracks registers and pointer types, checks memory access bounds, validates helper arguments, examines reachable control-flow paths and enforces program-type rules.

Modern correction: “eBPF cannot use loops” is outdated. Modern kernels permit bounded loops and other loop forms under verifier constraints. Complex state exploration can still cause rejection.

Maps

Maps are kernel objects that store typed key/value or specialized state. They allow persistent counters, blocklists, configuration, communication between programs and exchange with userspace.

Lifetime: A map lives while referenced by file descriptors, programs or a pin in BPF filesystem. Pinning under /sys/fs/bpf makes it discoverable beyond one process lifetime.

Interactive verifier challenge

A. Program reads data + 42 after checking only that data + 20 <= data_end.
B. Program looks up a key in a map, checks the returned pointer for NULL, then reads the value.
C. XDP program calls a helper that is not allowed for XDP programs.
D. Program uses a loop whose maximum iterations are provably bounded by 16.

Hook point: XDP

What is XDP, and what does it do?

Definition: XDP (eXpress Data Path) is an eBPF-based ingress processing path attached to a network device. A program runs for each received frame at an early point and returns an XDP action.

Common actions

  • XDP_PASS — continue into the normal stack.
  • XDP_DROP — discard early.
  • XDP_TX — transmit back through the same interface.
  • XDP_REDIRECT — redirect to another device, CPU or AF_XDP socket through supported mechanisms.
  • XDP_ABORTED — abnormal result, treated as drop and useful for diagnostics.

Execution modes

  • Native/driver: implemented by the network driver; normal production fast path.
  • Generic/SKB: compatibility path later than driver XDP; useful for learning and unsupported drivers.
  • Hardware offload: program executes on capable NIC hardware; support and helper set are device-specific.

Early-drop concept

Performance claim discipline: XDP can avoid later stack work, but actual packets-per-second, latency and CPU savings depend on driver mode, program complexity, CPU, NUMA, map contention, packet size and test methodology.

Real-world use cases

DDoS prefilter

Drop known-bad sources or malformed traffic before expensive protocol processing.

Load balancing

Hash flows and redirect frames toward backend interfaces or CPUs.

Telemetry

Count protocol, source or action data in maps with very early visibility.

Hook point: Traffic Control

What is TC, and what does eBPF do there?

Definition: Linux Traffic Control (TC) is the networking subsystem for queueing, shaping, scheduling, policing and filtering. eBPF programs can act as TC classifiers or actions, commonly attached through a clsact qdisc at ingress or egress.

Why choose TC BPF?

  • Need both ingress and egress processing.
  • Need an skb context and richer stack metadata.
  • Need packet modification, encapsulation or integration with qdisc behavior.
  • Need compatibility across devices where native XDP is unavailable.

Typical actions

  • TC_ACT_OK — continue.
  • TC_ACT_SHOT — drop.
  • TC_ACT_REDIRECT — redirect after a redirect helper.
  • Modify headers or metadata using helpers permitted for the program type.
TC is not only eBPF. TC existed long before eBPF and includes qdiscs, classes and traditional classifiers. eBPF is one programmable classifier/action mechanism within that subsystem.

Real-world use cases

Container networking policy, egress control, DSCP marking, service-mesh data paths, tunnel encapsulation/decapsulation, traffic accounting and QoS-aware classification.

Hook point: Workload boundary

What is cgroup, and what does eBPF do there?

Definition: Linux control groups (cgroups) organize processes in a hierarchy for resource control, accounting and delegation. eBPF can attach to cgroup-associated hooks so policy follows the workload rather than a particular interface.

cgroup_skb

Inspect and allow/drop packets associated with a cgroup at ingress or egress.

cgroup_sock_addr

Run on operations such as connect or bind; allow, deny or in some cases rewrite address arguments.

Other cgroup types

Socket creation, device access, socket options and sysctl access have distinct program types and semantics.

Return values are not universal. For example, common cgroup network hooks use 1 for allow and 0 for deny/drop, while other eBPF program types have completely different return codes. Always check the exact program and attach type.

Real-world use case

A container platform can attach policy to a workload cgroup. Every process placed in that cgroup inherits the connection policy even if its PID changes or it uses multiple interfaces. This is often a better policy identity than “traffic on eth0.”

Hook point: Endpoint

Socket filters and related socket hooks

Classic eBPF socket filter definition: a BPF_PROG_TYPE_SOCKET_FILTER program attaches to a socket and processes packets received by that socket. Its return value controls how many bytes are kept; returning 0 discards the packet for that socket.

Use it for

  • Capture filtering and per-socket packet selection.
  • Reducing data copied to a packet-capture application.
  • Protocol-aware observation for a specific endpoint.

Do not overgeneralize

  • It is not automatically a system-wide firewall.
  • It is not called for outgoing packets in the classic socket-filter program type.
  • Other socket-related BPF types—sockops, sk_skb, sk_msg, reuseport—solve different problems.
Toolchain

bpftool, bpftrace and libbpf

🔎 bpftool

The kernel-oriented inspection and management CLI. Use it to probe features, list programs/maps/links/BTF, dump map data, load/pin objects and inspect cgroup attachments.

sudo bpftool feature probe
sudo bpftool prog show
sudo bpftool map show
sudo bpftool link show
sudo bpftool btf show

🩺 bpftrace

A high-level tracing language and runtime for rapid observability. It is excellent for questions like “which process is calling this syscall?” without building a full C application.

sudo bpftrace -l 'tracepoint:syscalls:sys_enter_*'
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_execve {
  printf("%d %s %s\n", pid, comm, str(args.filename));
}'

🧱 libbpf

The reference C library for loading and managing BPF programs. It supports BPF object skeletons and CO-RE, which uses BTF to make compiled programs more portable across compatible kernel type layouts.

clang -O2 -g -target bpf -c program.bpf.c -o program.bpf.o
bpftool gen skeleton program.bpf.o > program.skel.h

Lab 2 — XDP ICMP early-drop with counters

Goal: create an isolated veth topology, prove ping works, attach a bounds-checked XDP program in generic mode, observe drops and map counters, then restore service.

1. Create isolated topology

sudo ip netns add s4-peer
sudo ip link add s4-host type veth peer name s4-peer0
sudo ip link set s4-peer0 netns s4-peer
sudo ip addr add 10.44.0.1/24 dev s4-host
sudo ip link set s4-host up
sudo ip netns exec s4-peer ip addr add 10.44.0.2/24 dev s4-peer0
sudo ip netns exec s4-peer ip link set lo up
sudo ip netns exec s4-peer ip link set s4-peer0 up
ping -c 2 10.44.0.2

Expected before attachment: two ICMP replies and 0% packet loss.

2. Write and compile the XDP program

mkdir -p ~/session4-ebpf && cd ~/session4-ebpf
cat > xdp_icmp_drop.bpf.c <<'C'
#include <linux/bpf.h>
#include <linux/if_ether.h>
#include <linux/ip.h>
#include <linux/icmp.h>
#include <linux/in.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_endian.h>

struct {
    __uint(type, BPF_MAP_TYPE_ARRAY);
    __uint(max_entries, 2);
    __type(key, __u32);
    __type(value, __u64);
} s4_xdp_counts SEC(".maps");

enum { PASS_COUNT = 0, DROP_COUNT = 1 };

SEC("xdp")
int xdp_drop_icmp_echo(struct xdp_md *ctx)
{
    void *data = (void *)(long)ctx->data;
    void *data_end = (void *)(long)ctx->data_end;
    struct ethhdr *eth = data;
    __u32 key;
    __u64 *value;

    if ((void *)(eth + 1) > data_end)
        return XDP_ABORTED;

    if (eth->h_proto == bpf_htons(ETH_P_IP)) {
        struct iphdr *ip = (void *)(eth + 1);
        if ((void *)(ip + 1) > data_end)
            return XDP_ABORTED;

        if (ip->protocol == IPPROTO_ICMP) {
            __u32 ihl_len = ip->ihl * 4;
            if (ihl_len < sizeof(*ip))
                return XDP_ABORTED;
            struct icmphdr *icmp = (void *)ip + ihl_len;
            if ((void *)(icmp + 1) > data_end)
                return XDP_ABORTED;
            if (icmp->type == ICMP_ECHO) {
                key = DROP_COUNT;
                value = bpf_map_lookup_elem(&s4_xdp_counts, &key);
                if (value)
                    __sync_fetch_and_add(value, 1);
                return XDP_DROP;
            }
        }
    }

    key = PASS_COUNT;
    value = bpf_map_lookup_elem(&s4_xdp_counts, &key);
    if (value)
        __sync_fetch_and_add(value, 1);
    return XDP_PASS;
}

char LICENSE[] SEC("license") = "GPL";
C

clang -O2 -g -target bpf -c xdp_icmp_drop.bpf.c -o xdp_icmp_drop.bpf.o
llvm-objdump -S xdp_icmp_drop.bpf.o | sed -n '1,80p'
Lab parser scope: this small program handles untagged Ethernet + IPv4 + ICMP echo only. A production parser must define behavior for VLANs, IPv6, fragments, options and malformed traffic.

3. Attach and test

sudo ip netns exec s4-peer ip link set dev s4-peer0 xdpgeneric \
  obj "$HOME/session4-ebpf/xdp_icmp_drop.bpf.o" sec xdp
sudo ip netns exec s4-peer ip -details link show dev s4-peer0
sudo ip netns exec s4-peer bpftool net show dev s4-peer0

ping -c 3 -W 1 10.44.0.2 || true
sudo bpftool map show name s4_xdp_counts
MAP_ID=$(sudo bpftool map show name s4_xdp_counts | sed -n '1s/:.*//p')
sudo bpftool map dump id "$MAP_ID"
Expected output and interpretation
  • ip -details link inside the peer namespace shows an XDP attachment in generic mode.
  • Ping shows 100% packet loss because echo requests entering s4-host are dropped.
  • The array map has two entries. Key 1 (drop counter) increases. Values are displayed as bytes and/or decoded values depending on BTF/tool version.
  • Non-ICMP traffic would return XDP_PASS.

4. Roll back and clean up

sudo ip netns exec s4-peer ip link set dev s4-peer0 xdpgeneric off
ping -c 2 10.44.0.2
sudo ip link del s4-host
sudo ip netns del s4-peer
sudo bpftool net show
sudo bpftool map show name s4_xdp_counts || true

Expected: ping works after detach; deleting the veth and namespace removes the topology; the unpinned map disappears when no references remain.

Lab 3 — TC ingress policy for TCP/8080

Goal: prove TC BPF can enforce ingress policy after an skb exists and expose action statistics.

1. Build a namespace service

sudo ip netns add s4-web
sudo ip link add s4-client type veth peer name s4-server
sudo ip link set s4-server netns s4-web
sudo ip addr add 10.45.0.1/24 dev s4-client
sudo ip link set s4-client up
sudo ip netns exec s4-web ip addr add 10.45.0.2/24 dev s4-server
sudo ip netns exec s4-web ip link set lo up
sudo ip netns exec s4-web ip link set s4-server up
sudo ip netns exec s4-web sh -c 'nohup python3 -m http.server 8080 --bind 10.45.0.2 >/tmp/s4-http.log 2>&1 & echo $! >/tmp/s4-http.pid'
curl --max-time 2 http://10.45.0.2:8080/ | head

Expected before policy: an HTML directory listing.

2. Compile classifier

cd ~/session4-ebpf
cat > tc_block_8080.bpf.c <<'C'
#include <linux/bpf.h>
#include <linux/pkt_cls.h>
#include <linux/if_ether.h>
#include <linux/ip.h>
#include <linux/tcp.h>
#include <linux/in.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_endian.h>

SEC("classifier")
int block_tcp_8080(struct __sk_buff *skb)
{
    void *data = (void *)(long)skb->data;
    void *data_end = (void *)(long)skb->data_end;
    struct ethhdr *eth = data;

    if ((void *)(eth + 1) > data_end)
        return TC_ACT_OK;
    if (eth->h_proto != bpf_htons(ETH_P_IP))
        return TC_ACT_OK;

    struct iphdr *ip = (void *)(eth + 1);
    if ((void *)(ip + 1) > data_end || ip->protocol != IPPROTO_TCP)
        return TC_ACT_OK;
    __u32 ihl_len = ip->ihl * 4;
    if (ihl_len < sizeof(*ip))
        return TC_ACT_OK;

    struct tcphdr *tcp = (void *)ip + ihl_len;
    if ((void *)(tcp + 1) > data_end)
        return TC_ACT_OK;

    return tcp->dest == bpf_htons(8080) ? TC_ACT_SHOT : TC_ACT_OK;
}

C
clang -O2 -g -target bpf -c tc_block_8080.bpf.c -o tc_block_8080.bpf.o

3. Attach inside namespace and verify

sudo ip netns exec s4-web tc qdisc add dev s4-server clsact
sudo ip netns exec s4-web tc filter add dev s4-server ingress \
  bpf direct-action obj "$HOME/session4-ebpf/tc_block_8080.bpf.o" sec classifier

curl --max-time 2 http://10.45.0.2:8080/ || true
sudo ip netns exec s4-web tc -s filter show dev s4-server ingress
Expected output
  • Curl times out or reports a connection failure because inbound TCP/8080 packets are dropped.
  • tc -s filter show displays the BPF filter and increasing packet/byte/drop statistics. Formatting varies by iproute2 version.
  • Traffic to other ports is not dropped by this program.

4. Cleanup

sudo ip netns exec s4-web tc qdisc del dev s4-server clsact
sudo ip netns exec s4-web sh -c 'kill $(cat /tmp/s4-http.pid) 2>/dev/null || true'
sudo ip link del s4-client
sudo ip netns del s4-web

Lab 4 — cgroup connect policy for TCP/9090

Goal: deny outbound connection attempts made by processes in one cgroup while leaving other processes unaffected.

This lab requires cgroup v2 and a kernel/bpftool build supporting cgroup/connect4. Use Lab 0 evidence before proceeding.

1. Start a local service and prove baseline

cd ~/session4-ebpf
nohup python3 -m http.server 9090 --bind 127.0.0.1 >/tmp/s4-9090.log 2>&1 &
echo $! > /tmp/s4-9090.pid
curl --max-time 2 http://127.0.0.1:9090/ | head

2. Compile and load the cgroup program

cat > cgroup_block_9090.bpf.c <<'C'
#include <linux/bpf.h>
#include <linux/in.h>
#include <linux/socket.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_endian.h>

SEC("cgroup/connect4")
int block_connect_9090(struct bpf_sock_addr *ctx)
{
    if (ctx->protocol == IPPROTO_TCP && bpf_ntohl(ctx->user_port) == 9090)
        return 0; /* deny */
    return 1;     /* allow */
}

char LICENSE[] SEC("license") = "GPL";
C
clang -O2 -g -target bpf -c cgroup_block_9090.bpf.c -o cgroup_block_9090.bpf.o
sudo mkdir -p /sys/fs/cgroup/session4_lab
sudo rm -f /sys/fs/bpf/session4_block_9090
sudo bpftool prog load cgroup_block_9090.bpf.o /sys/fs/bpf/session4_block_9090
sudo bpftool cgroup attach /sys/fs/cgroup/session4_lab connect4 \

sudo bpftool cgroup show /sys/fs/cgroup/session4_lab

3. Compare outside and inside the cgroup

echo "Outside cgroup — should succeed"
curl --max-time 2 http://127.0.0.1:9090/ | head -n 1

echo "Inside cgroup — should be denied"
sudo bash -c '
  echo $$ > /sys/fs/cgroup/session4_lab/cgroup.procs
  curl --max-time 2 http://127.0.0.1:9090/
' || true
Expected behavior

The normal shell reaches the service. The shell moved into session4_lab receives a connection error, commonly “Operation not permitted” or a curl failure that reflects denial by the connect hook. Exact text varies by libc and curl.

4. Detach and remove all state

Production thinking

From demo to production

Change safety

  • Test in namespace or canary interface.
  • Keep out-of-band access.
  • Define attach, verify, detach and rollback commands.
  • Pin only intentional long-lived objects.
  • Use idempotent loaders and lifecycle-aware BPF links where possible.

Correctness

  • Parse packet headers with bounds checks.
  • Handle VLANs, IPv6, fragmentation and extension headers if in scope.
  • Specify byte order explicitly.
  • Document return-code semantics per hook.
  • Test pass, drop, malformed and boundary inputs.

Performance

  • Measure in the intended XDP mode.
  • Avoid hot shared-map contention.
  • Prefer per-CPU counters when appropriate.
  • Profile program cost and map lookups.
  • Monitor drops, aborts and verifier/JIT behavior.

Defense-in-depth positioning

eBPF enforcement should complement—not casually replace—nftables, routing policy, namespaces, LSMs, application controls and monitoring. Choose each control for the visibility, lifecycle and failure mode it handles best.

Validation record

Technical accuracy and simulation validation

Accuracy controls applied

  • Separated the eBPF runtime from its hook points.
  • Used program-type-specific return semantics.
  • Described modern bounded-loop support rather than the obsolete “no loops” rule.
  • Distinguished XDP native, generic and offload modes.
  • Explicitly limited generic-XDP performance conclusions.
  • Included packet bounds checks and network-byte-order handling in lab code.
  • Included before/after evidence and cleanup for every state-changing lab.

Interactive simulation limits

  • Packet journey work units are conceptual.
  • Animations do not emulate kernel timing or throughput.
  • Map simulator demonstrates key/value behavior, not concurrency or exact kernel memory layout.
  • Actual commands remain authoritative; outputs vary by kernel, driver, tool and distribution.
