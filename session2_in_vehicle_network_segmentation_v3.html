Walk through a simplified attack path. The purpose is not to claim every vehicle is built this way; it is to show why architectural boundaries matter.

Vehicle zones, explained simply

A “zone” here means a security and functional boundary. Production architectures may be domain-based, physically zonal, centralized, or hybrid.

What lives here?

Head unit, media, navigation UI, smartphone integration, Bluetooth, Wi-Fi, USB and sometimes rear-seat entertainment.

Why it is exposed: it parses content and communicates with users, phones and removable devices.

Analogy

The hotel lobby: useful and public-facing, but guests do not receive keys to the boiler room.

Typical policy: no direct command path to critical control ECUs.

What lives here?

Telematics control unit, cellular connectivity, eCall, GNSS, remote services, fleet telemetry and OTA transport functions.

Why it matters: this zone connects the vehicle to off-board systems.

Analogy

The building’s internet edge: valuable, monitored, patched and never assumed trustworthy merely because it is “inside”.

Risk: a remote-facing component can become an ingress point.

What lives here?

Cameras, radar, lidar, ultrasonic sensing, perception/fusion processors and driver-assistance controllers.

Traffic character: high data volume, time sensitivity, integrity requirements and controlled actuation paths.

Analogy

The building’s safety-control room: alarms and automated decisions must be timely and protected from casual traffic.

What lives here?

Engine, transmission, torque coordination, battery management, inverter/motor control and drivetrain-related functions.

Security objective: preserve authorized control, message integrity and predictable behavior.

Analogy

The machinery room: a visitor may view a status display, but cannot directly alter pumps or motors.

What lives here?

Service access, fault reading, ECU programming, calibration and maintenance workflows over controlled diagnostic paths.

Special concern: diagnostics is legitimate privileged access, so authorization, session controls, logging and physical/service context matter.

Analogy

The maintenance entrance: powerful tools are permitted, but only for authorized technicians and approved tasks.

Domain architecture versus zonal architecture

“Powertrain zone” and “front-left zonal controller” describe different grouping ideas. A domain groups functions; a physical zone groups equipment by vehicle location.

Simple version: older designs often connect computers by job. Newer zonal designs increasingly connect nearby devices to a local controller, then use high-speed backbones to central compute.

Domain-oriented architecture

ECUs are grouped around functions such as body, powertrain, infotainment and ADAS.

Door ECULighting ECUBody domainEngine ECUPowertrain domainADAS ECU
Trade-off: functional ownership is clear, but wiring may cross large parts of the vehicle.

Physical zonal architecture

Nearby sensors and actuators connect to front/rear or left/right zonal controllers, which connect to central compute over Ethernet.

Front-left zoneFront-right zoneRear zoneCentral computeVehicle cloud gateway
Benefit: shorter local wiring and a clearer high-speed backbone; software and safety partitioning become crucial.

Security consequence

A physical zonal controller can aggregate signals belonging to several functional domains. Security policy must therefore consider function, location, message type, vehicle state and destination, not only which box a cable enters.

Migration reality

Many production vehicles are hybrid: legacy CAN/LIN networks remain behind domain or zonal controllers while Automotive Ethernet links gateways, compute platforms and service-oriented applications.

Automotive Ethernet and VLAN segmentation

Automotive Ethernet provides switched, full-duplex IP communication suitable for service-oriented applications, high-bandwidth sensors, diagnostics and software updates.

Physical and link concepts

  • Single-pair Ethernet: automotive PHY families such as 100BASE-T1 and 1000BASE-T1 use one twisted pair.
  • Switching: traffic can be forwarded only toward the relevant port rather than broadcast across a shared bus.
  • VLAN: an IEEE 802.1Q tag can create logical Layer-2 broadcast domains.
  • QoS: priority and shaping help protect important traffic, but require engineering and validation.

Protocol stack: where each control lives

ApplicationSOME/IP, diagnostics, update services
TransportUDP or TCP
NetworkIPv4/IPv6, multicast, routing
Data linkEthernet MAC, VLAN, priority
Physical100BASE-T1 / 1000BASE-T1 and cabling
Critical distinction: a VLAN separates Layer-2 traffic. It does not authenticate ECUs, authorize services, inspect application messages or replace an inter-zone firewall.

CAN and FlexRay: two different scheduling ideas

CAN — priority-based shared bus

  • ECUs broadcast frames on a shared bus.
  • The identifier represents message meaning and arbitration priority, not an IP-style destination.
  • During arbitration, a lower numerical CAN identifier has higher priority.
  • Classic CAN does not itself provide cryptographic sender authentication.
Analogy: several speakers start together; the predefined highest-priority announcement continues while others pause and retry.

FlexRay — synchronized communication cycle

  • Designed for deterministic, time-driven communication.
  • A communication cycle includes a static segment and may include a dynamic segment.
  • Nodes synchronize clocks and transmit in defined opportunities.
  • Segmentation and application-layer protections are still required.
Analogy: a railway timetable gives critical trains reserved slots, instead of making every train compete at the junction.

Security realityNeither should be treated as an authorization system; use architecture, gateways and higher-layer security.

SOME/IP and service discovery

SOME/IP is a service-oriented automotive communication protocol over IP. SOME/IP-SD defines how services are offered, found, subscribed to and stopped.

Core vocabulary

  • Service: a logical capability, identified by a Service ID.
  • Instance: a concrete provider instance.
  • Method: request/response interaction.
  • Event: server-originated update.
  • Eventgroup: a group a client can subscribe to.
  • OfferService / FindService: key discovery messages.

Animated discovery flow

Security boundary: discovery is not authorization. A client finding a service does not automatically mean it should be permitted to use it.

UDS and DoIP: controlled diagnostic power

Unified Diagnostic Services (UDS) defines diagnostic services independent of the underlying data link. DoIP carries diagnostic communication over IP and enables discovery, routing activation and diagnostic transport through a DoIP entity or gateway.

DoIP journey

Workshop tester→UDP discovery
Vehicle / DoIP entity→TCP connection
Routing activation→Target ECU
Bad design: successful network connection grants unrestricted access to every ECU.
Better design: authenticate the tester/workflow, validate vehicle state, activate only permitted routes and audit the session.
Teaching boundary: UDS service availability, sub-functions, timing parameters and negative response codes are ECU/program-specific. DoIP transport security can include TLS depending on implementation and profile; do not assume every deployed DoIP link is encrypted.

AUTOSAR SecOC: authenticity, integrity and freshness

SecOC protects selected Protocol Data Units (PDUs) using an authenticator and freshness information. It is designed to make critical onboard messages verifiable, not to provide confidentiality by default.

1. Authentic payload

The application data that must be protected, such as a status or command PDU.

2. Freshness value

A counter, trip value, timer-derived value or managed combination helps receivers identify stale/replayed traffic.

3. Authenticator

A message authentication code is computed from configured inputs, usually including protected data and freshness.

Network segmentation limits movement between ECUs; secure boot reduces the chance that an ECU starts unauthorized software. Both layers are needed.

Secure OTA workflow

  1. OEM/update authority creates a signed package and manifest.
  2. Telematics transports it; transport alone does not establish package trust.
  3. Update manager validates signature, target, dependencies and version.
  4. Vehicle-state policy decides whether installation may proceed.
  5. Target installs with rollback/recovery protection.
  6. Health status and result are reported and audited.

In-vehicle IDS and monitoring

Detection complements prevention. Useful telemetry includes gateway decisions, diagnostic attempts, new services, message rates, invalid authenticators and vehicle-state mismatches.

What can be monitored?

  • Unknown or unexpected CAN identifiers
  • Abnormal frequency or timing
  • Impossible signal values or state transitions
  • Repeated UDS SecurityAccess failures
  • Unexpected SOME/IP providers or subscription floods
  • SecOC MAC/freshness failures
  • Blocked cross-zone flows
  • Update verification or rollback events

Create secoc_demo.py

cat > secoc_demo.py <<'PY'
#!/usr/bin/env python3
import hmac, hashlib, json

KEY = bytes.fromhex("00112233445566778899AABBCCDDEEFF")
last_accepted = 100

def make_pdu(payload: str, freshness: int):
    authenticated = f"{payload}|{freshness}".encode()
    mac = hmac.new(KEY, authenticated, hashlib.sha256).hexdigest()[:16]
    return {"payload": payload, "freshness": freshness, "mac": mac}

def verify(pdu):
    global last_accepted
    authenticated = f"{pdu['payload']}|{pdu['freshness']}".encode()
    expected = hmac.new(KEY, authenticated, hashlib.sha256).hexdigest()[:16]
    if not hmac.compare_digest(expected, pdu["mac"]):
        return "REJECT: authentication/integrity failure"
    if pdu["freshness"] <= last_accepted:
        return f"REJECT: stale freshness {pdu['freshness']} <= {last_accepted}"
    last_accepted = pdu["freshness"]
    return f"ACCEPT: payload={pdu['payload']} freshness={pdu['freshness']}"

fresh = make_pdu("TorqueRequest=12", 101)
print("FRESH  ", json.dumps(fresh), "=>", verify(fresh))

print("REPLAY ", json.dumps(fresh), "=>", verify(fresh))

tampered = dict(make_pdu("TorqueRequest=12", 102))
tampered["payload"] = "TorqueRequest=99"
print("TAMPER ", json.dumps(tampered), "=>", verify(tampered))
PY

Discussion

  • Why is the replay MAC still valid? Because it is an exact copy of a previously authentic message.
  • What stops it? The receiver’s freshness acceptance rule.
  • What happens after ECU reset or counter loss? Freshness synchronization and persistence become design concerns.

Create the rate monitor

cat > can_rate_monitor.py <<'PYCODE'
#!/usr/bin/env python3
import socket, struct, time
from collections import Counter

THRESHOLD = 25
FMT = "=IB3x8s"
SIZE = struct.calcsize(FMT)
sock = socket.socket(socket.PF_CAN, socket.SOCK_RAW, socket.CAN_RAW)
sock.bind(("vcan0",))
counts = Counter()
window = time.monotonic()
print(f"Monitoring vcan0; alert threshold={THRESHOLD} frames/sec per ID")

while True:
    frame = sock.recv(SIZE)
    can_id, dlc, data = struct.unpack(FMT, frame)
    arbitration_id = can_id & 0x1FFFFFFF
    counts[arbitration_id] += 1
    now = time.monotonic()
    if now - window >= 1.0:
        for ident, rate in sorted(counts.items()):
            verdict = "ALERT" if rate > THRESHOLD else "OK"
            print(f"{verdict:5} ID=0x{ident:03X} rate={rate}/s")
        counts.clear()
        window = now
