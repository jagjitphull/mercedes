01A

Linux Resource City

Meet the five departments every cgroup operator must keep under control. Change demand, trigger incidents and choose evidence-driven controls.

Scenario console
⚡CPU Powercpu.stat · cpu.pressure
🏬Memory Storememory.events · PSI
🚦I/O Highwayio.stat · io.pressure
🏘️Task Officepids.current · events
🏰Network GateBPF · TC · XDP · nft

Simple explanation

Cgroups are neighbourhood rules: busy workloads may use spare resources, but limits and priorities keep one noisy neighbour from ruining the city.

Administrator explanation

Use weights for relative sharing, limits for containment, protection for critical memory and PSI plus controller counters to prove whether workloads are actually waiting.

Kernel-level explanation

The unified hierarchy distributes controller state through ancestors. Effective behaviour is constrained by parent configuration, task placement, scheduler/reclaim paths and available hook context.

Hot take: CPU weight is a negotiation; CPU quota is a ceiling. Confusing the two is how well-meaning administrators accidentally manufacture latency.
02

The mental model

cgroup is not a virtual machine and not a security boundary by itself. It is a kernel mechanism that places processes in a hierarchy and applies resource policy to that hierarchy.

👥
Group
Put related processes together.
📏
Measure
Account CPU, memory, I/O and tasks.
🚦
Control
Weight, cap, protect or allocate.
🔭
Observe
Read counters, events and pressure.
Limits

“Do not exceed this.”

cpu.max, memory.max, io.max and pids.max impose upper boundaries. A CPU limit throttles; a memory hard limit may eventually trigger cgroup OOM handling.

Weights

“Prefer this group when busy.”

cpu.weight and io.weight are relative shares among active siblings. They are work-conserving: idle groups do not reserve unused capacity.

Protection

“Reclaim elsewhere first.”

memory.low provides best-effort protection; memory.min is stronger. These are not reservations of physical RAM in the ordinary sense.

Important distinction: namespaces change what a process can see; cgroups govern how much it can use and account for that use. Containers normally combine both, plus capabilities, LSMs and other controls.
03

Architecture and rule flow

The core organizes processes. Controllers implement resource-specific behavior. User space writes policy through a pseudo-filesystem, normally mounted at /sys/fs/cgroup.

Four moving parts

  1. cgroup core: hierarchy, membership, migration, delegation and lifecycle.
  2. controllers: CPU, memory, I/O, PIDs, cpusets and optional hardware-specific resources.
  3. cgroupfs: directories are groups; files expose controls and counters.
  4. manager: usually systemd, a container runtime or an orchestrator.

Process lifecycle

parent process [cgroup A] │ fork() ▼ child starts in [cgroup A] │ write PID → B/cgroup.procs ▼ child moves to [cgroup B] Existing descendants do not move automatically.

Hierarchical

A child can further restrict what its parent granted, but cannot escape an ancestor’s limit.

Dynamic

Limits and weights can change while workloads run. Frequent process migration is discouraged.

Process-aware

Writing any thread ID to cgroup.procs moves the whole process in normal domain mode.

Event-driven

*.events, PSI and polling allow managers to react to pressure, empty groups and limit hits.

04

cgroup v1 versus v2

Modern systems should normally use v2. v1 remains relevant when auditing older hosts, legacy agents or migration problems.

Version 1 · legacy

Multiple controller trees

/sys/fs/cgroup/ ├── cpu/ ├── app-A ├── memory/ ├── app-A ├── blkio/ └── app-A └── pids/

One process may occupy different paths in different controller hierarchies. Interfaces and behavior vary more between controllers.

complex compositionlegacy names
→
Version 2 · preferred

One unified tree

/sys/fs/cgroup/ ├── system.slice/ │ └── app.service/ └── user.slice/ └── user-1000.slice/

Every process has one unified cgroup path. Controllers share hierarchy rules, delegation is safer, and newer controls such as PSI integration are available.

single hierarchyconsistent model

Identify the active version

Shell · reliable checks
stat -fc %T /sys/fs/cgroup
# cgroup2fs = v2; tmpfs commonly indicates v1 controller mounts below it

findmnt -t cgroup,cgroup2
cat /proc/self/cgroup

On v2, /proc/self/cgroup contains an entry shaped like 0::/some/path. A hybrid system can have both v1 and v2 mounts; do not infer “pure v2” from one file alone.

05

Core cgroup v2 interface

Select a category. These files exist independently of a specific resource controller, although availability can depend on kernel version and configuration.

Top-down rule: a child can enable only controllers that its parent has made available through the parent’s cgroup.subtree_control. For domain controllers, a non-root group normally cannot both contain processes and distribute resources to children—the “no internal process” rule.
Domain mode

Processes stay together

Normal cgroups are resource domains. All threads of a process occupy the same group, and domain controllers such as memory apply to the process-level hierarchy. This is the ordinary service/container model.

Threaded mode

Selected controllers can split threads

A threaded subtree permits individual threads to occupy different child cgroups while sharing one resource domain. Threaded-capable controllers include CPU, cpuset, perf_event and PIDs. Memory remains a domain resource.

Delegation

Hand over a subtree, not the machine

A delegate may create descendants and move its own workloads inside the delegated boundary, but ancestor policy still wins. Safe delegation does not grant writes to controls that distribute the parent’s resources.

cgroup namespaces

Virtualize the visible root

A cgroup namespace can present a delegated cgroup as / to a container and hide host hierarchy paths. It changes visibility and migration reachability; it does not create a second resource universe.

PSI

Measure lost time, not just consumption

some means at least one task is stalled; full means all non-idle tasks are stalled simultaneously. System-wide CPU full is reported as zero for compatibility, while per-cgroup CPU pressure can still distinguish full-group stalls.

Resource ownership

Migration is not retroactive accounting

Stateful charges such as memory pages or miscellaneous device resources can remain with the cgroup where they were first charged. Design the hierarchy before workload start instead of continuously shuffling PIDs.

06

Controller explorer

The exact controller list is kernel-, configuration- and hardware-dependent. Read cgroup.controllers on the target host rather than assuming every controller exists.

Devices are different in v2: the v1 devices controller file interface is not reproduced as a normal v2 controller. Device access control is commonly enforced by a cgroup BPF device program, usually managed by systemd or a container runtime.

Observability and Pressure Stall Information

Resource usage tells you how much was consumed. PSI tells you how much time useful work lost while waiting for CPU, memory or I/O.

Repeatable observation cycle

BaselineRecord current, stat, events and pressure.
ApplySet one policy at a time.
PressureGenerate controlled load.
CompareExplain changed counters.

Read PSI correctly

  • some: at least one non-idle task is stalled.
  • full: all non-idle tasks in scope are stalled together. System-wide CPU full is defined as zero for compatibility; per-cgroup CPU full can still be useful.
  • avg10/60/300: percentage of wall time stalled over rolling windows.
  • total: cumulative stall time in microseconds.

CPU pressure normally reports some; memory and I/O can report both some and full.

Interactive PSI interpretation

Is the workload merely busy—or actually stalled?

printf '%s
' '=== memory ==='
cat "$CG/memory.current" "$CG/memory.events" 2>/dev/null || true
cat "$CG/memory.pressure" 2>/dev/null || true
printf '%s
' '=== I/O and tasks ==='

Containers do not replace cgroups. The runtime and orchestrator create and manage cgroups on the workload’s behalf.

Docker verification

  • Check CgroupVersion and CgroupDriver.
  • Use docker stats for a convenient view.
  • Then verify the host cgroup files for authoritative limits and events.
  • Rootless resource flags require cgroup v2 plus systemd support; otherwise flags may be ignored.

Kubernetes distinctions

  • Requests influence scheduling and relative allocation.
  • CPU limits normally use CFS bandwidth enforcement.
  • Memory limits create a containment boundary.
  • Guaranteed, Burstable and BestEffort QoS affect grouping and eviction priority.
  • Memory QoS is a separate opt-in alpha feature, not an assumption.

12

How cgroups appear in the real world

You often use cgroups indirectly through a higher-level manager.

system services

Protect a database

Give the database higher CPU and I/O weight, protect a working set with MemoryLow, and cap noncritical batch services.

containers

Docker limits

--cpus, --memory, --pids-limit and block-I/O options are translated by the runtime into cgroup policy.

orchestration

Kubernetes QoS

The kubelet and runtime use cgroups to enforce pod/container CPU and memory requests and limits. Exact paths and values depend on the cgroup driver and runtime.

CI/CD

Contain build storms

Limit parallel tasks and CPU bandwidth so a runaway compiler or test fan-out does not starve SSH, monitoring or production workloads.

multi-user systems

User and tenant slices

Apply aggregate policy to user-1000.slice or custom tenant slices rather than trying to limit every command separately.

observability

Pressure, not just usage

CPU can be “100% used” without user-visible distress. PSI reports time lost because runnable work stalled for CPU, memory or I/O.

Docker and Kubernetes examples
# Docker: half a CPU, 256 MiB RAM, maximum 64 tasks
sudo docker run --rm --cpus=0.5 --memory=256m --pids-limit=64 alpine:latest sh -c 'sleep 300'

# Kubernetes: requests influence placement/relative allocation; limits cap usage
resources:
  requests:
    cpu: "250m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "256Mi"
13

Advanced placement, lifecycle and delegation

These features matter for low-latency systems, rootless containers and nested managers. They are also where hierarchy mistakes become easiest to make.

cpuset and NUMA

cpuset.cpus and cpuset.mems constrain where work runs and allocates memory. Always verify the *.effective files because ancestors and hotplug can narrow the requested set.

  • Affinity selects CPUs for a task; cpuset constrains a whole hierarchy.
  • Remote NUMA memory can add latency even when CPU pinning is correct.
  • Partition roots and isolated partitions are kernel/version dependent.

Delegation boundary

Delegate=yes lets a unit manage a controlled subtree. The delegate can organize descendants but cannot escape ancestor limits.

  • Delegate a subtree, not all of cgroupfs.
  • Do not solve permissions with recursive chmod.
  • Rootless container limits require an effective user-session delegation chain.

14

Cgroup-aware networking with eBPF, TC, XDP and Netfilter

cgroup v2 has no ordinary network-bandwidth controller. Modern workload-aware networking combines cgroup identity with BPF hooks, then uses TC, XDP or Netfilter according to where enforcement belongs.

Core model: cgroups answer “which workload?”; cgroup BPF answers “may this workload perform this network action?”; TC answers “how should packets on this interface be classified, shaped or redirected?”; XDP answers “can this receive-side packet be handled or dropped before most of the stack?”; Netfilter/nftables answers “what stateful firewall, conntrack or NAT policy applies?”
Workload identity

cgroup BPF

Attach policy to a cgroup subtree. Useful hooks include cgroup/connect4, connect6, bind4, bind6, and cgroup_skb/ingress or egress.

Interface + skb

TC / TCX

Runs on interface ingress or egress with an skb context. Suitable for classification, policing, shaping integration, marking, mirroring and redirecting.

Earliest receive path

XDP

Runs before most of the networking stack. Excellent for high-rate drop, redirect and load-balancing logic, but normally lacks final receiving-socket or process-cgroup identity.

Stateful host firewall

Netfilter / nftables

Provides INPUT, OUTPUT, FORWARD, conntrack and NAT semantics. A BPF Netfilter program type also exists on supporting kernels, but nftables remains the conventional operational interface.

Accuracy note: this visual shows decision layers and the most useful hook for each job. It is not a universal kernel call-order chart; exact ordering varies across IPv4/IPv6, local input/output, forwarding, encapsulation, offload, driver mode and kernel version.

Connection and bind authorization

Socket-address hooks run when a process performs an operation such as connect() or bind(). They are usually the clearest choice for per-service destination and listener policy because denial occurs before ordinary packet transmission.

web.service cgroup ├── connect TCP 443 → allow ├── connect TCP 25 → deny └── bind 0.0.0.0:22 → deny

Packet policy and accounting

cgroup_skb/egress and cgroup_skb/ingress receive an __sk_buff context for traffic associated with the cgroup. They suit per-workload packet filtering, counters and metadata-based policy.

container cgroup ├── DNS packets → count ├── approved subnet → allow └── other egress → reject

Hook-selection matrix

Choose the earliest hook that still has the context required for a correct decision. Earlier is not automatically better.

Modern v2 design

systemd slice / container cgroup │ cgroup BPF policy ▼ shared map, mark or endpoint identity │ ▼ TC / XDP / Netfilter enforcement

The control plane may coordinate programs through pinned BPF maps. Sharing is explicit design work; the hooks do not automatically exchange application identity.

Legacy cgroup v1 net_cls

The v1 net_cls controller writes a class identifier into packets so TC can classify them. It is useful when maintaining old systems, but it is not a normal cgroup v2 controller.

Legacy illustration — do not use on a v2-only lab
echo 0x100001 > net_cls.classid
tc filter add dev eth0 parent 1: protocol ip handle 1: cgroup

Verdicts and context

Each hook family has its own context object and return-value model.

cgroup socket / skb

1 generally allows and 0 rejects for the hooks used in these labs.

TC classifier/action

Common verdicts include TC_ACT_OK, TC_ACT_SHOT and redirect actions.

XDP

XDP_PASS, XDP_DROP, XDP_TX, XDP_REDIRECT and XDP_ABORTED.

Netfilter BPF

Firewall-style verdicts include NF_ACCEPT and NF_DROP.

TC versus TCX

Classic tc/classifier sections remain common; current libbpf documentation recommends TCX attach sections for new link-based designs where available.

Generic versus native XDP

xdpgeneric is portable for training but runs later than driver-native XDP and must not be used for native-mode performance claims.

Run the networking labs: the executable exercises are grouped in the main Hands-on labs → Networking labs A–C catalogue. Direct links: Lab A capability inspection, Lab B cgroup/connect4 filtering, and Lab C TC versus XDP.
Netfilter BPF scope: current kernels expose BPF_PROG_TYPE_NETFILTER and a netfilter ELF section. Treat it as an advanced, version-sensitive programming interface. For ordinary stateful firewalling, logging, conntrack and NAT training, nftables is still the clearer baseline.

Network Lab B (Lab 18) — Block one destination port for a systemd slice with cgroup/connect4
35 mincgroup v2deterministic local test

Goal: attach a small socket-address BPF program to a slice, allow local TCP port 8080, deny local TCP port 8443, and prove that unrelated processes remain unaffected.

1. Build the BPF program
cat >/tmp/cg_block8443.bpf.c <<'EOF'
#include <linux/bpf.h>
#include <linux/in.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_endian.h>

SEC("cgroup/connect4")
int block_tcp_8443(struct bpf_sock_addr *ctx)
{
    if (ctx->protocol == IPPROTO_TCP &&
        ctx->user_port == bpf_htons(8443))
        return 0; /* reject connect() */
    return 1;     /* allow */
}

char LICENSE[] SEC("license") = "GPL";
EOF

MULTIARCH="$(clang -print-target-triple | sed 's/-unknown//')"
INCLUDE=()
[ -n "$MULTIARCH" ] && [ -d "/usr/include/$MULTIARCH" ] && INCLUDE=(-I"/usr/include/$MULTIARCH")
clang -O2 -g -target bpf "${INCLUDE[@]}" \
  -c /tmp/cg_block8443.bpf.c -o /tmp/cg_block8443.bpf.o

sudo mountpoint -q /sys/fs/bpf || sudo mount -t bpf bpf /sys/fs/bpf
sudo rm -f /sys/fs/bpf/cg_block8443
sudo bpftool prog load /tmp/cg_block8443.bpf.o /sys/fs/bpf/cg_block8443
2. Create a slice, local servers and attach policy
sudo tee /etc/systemd/system/cgnet.slice >/dev/null <<'EOF'
[Unit]
Description=Cgroup networking training slice
[Slice]
CPUWeight=100
EOF
sudo systemctl daemon-reload
sudo systemctl start cgnet.slice

python3 -m http.server 8080 --bind 127.0.0.1 >/tmp/cg-net-8080.log 2>&1 &
P8080=$!
python3 -m http.server 8443 --bind 127.0.0.1 >/tmp/cg-net-8443.log 2>&1 &
P8443=$!
printf '%s %s\n' "$P8080" "$P8443" | sudo tee /tmp/cg-net-server.pids >/dev/null
sleep 1

CG_PATH="$(systemctl show -p ControlGroup --value cgnet.slice)"
CG="/sys/fs/cgroup${CG_PATH}"
test -n "$CG_PATH" && test -d "$CG"
sudo bpftool cgroup attach "$CG" connect4 pinned /sys/fs/bpf/cg_block8443 multi
sudo bpftool cgroup tree "$CG"
3. Verify allowed and denied behavior
# Port 8080: expected HTTP 200 inside the protected slice.
sudo systemd-run --quiet --wait --collect --pipe \
  --unit=cg-net-allow --slice=cgnet.slice \
  /usr/bin/curl -sS -o /dev/null -w 'HTTP=%{http_code}\n' \
  --max-time 3 http://127.0.0.1:8080/

# Port 8443: connect() should fail with EPERM before TCP succeeds.
sudo systemd-run --quiet --wait --collect --pipe \
  --unit=cg-net-deny --slice=cgnet.slice \
  /usr/bin/strace -f -e trace=connect \
  /usr/bin/curl -sS -o /dev/null --max-time 3 http://127.0.0.1:8443/ || true

# Outside the slice, the same 8443 server remains reachable.
curl -sS -o /dev/null -w 'outside HTTP=%{http_code}\n' \

Network Lab C (Lab 19) — Compare TC egress filtering with XDP ingress filtering in isolated namespaces

1. Build TC and XDP programs
cat >/tmp/tc_drop_icmp.bpf.c <<'EOF'
#include <linux/bpf.h>
#include <linux/if_ether.h>
#include <linux/ip.h>
#include <linux/in.h>
#include <linux/pkt_cls.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_endian.h>

SEC("tc")
int drop_icmp_egress(struct __sk_buff *skb)
{
    void *data = (void *)(long)skb->data;
    void *data_end = (void *)(long)skb->data_end;
    struct ethhdr *eth = data;
    if ((void *)(eth + 1) > data_end || eth->h_proto != bpf_htons(ETH_P_IP))
        return TC_ACT_OK;
    struct iphdr *ip = (void *)(eth + 1);
    if ((void *)(ip + 1) > data_end)
        return TC_ACT_OK;
    return ip->protocol == IPPROTO_ICMP ? TC_ACT_SHOT : TC_ACT_OK;
}
char LICENSE[] SEC("license") = "GPL";
EOF

CPU weight seems ineffectiveNo contention, groups are not siblings, tasks run on different CPUs, or scheduling classes differ.Pin competitors to the same CPU for the experiment and keep both continuously runnable.

          
memory.max did not instantly killThe kernel tries reclaim first; allocations, swap and page cache behavior vary.Watch memory.events, memory.current, memory.swap.current and memory.pressure.

          
I/O cap has no visible effectWrong block device, unsupported stack, buffered cache effects, or I/O is attributed elsewhere.Use lsblk, findmnt, iostat and io.stat; understand device-mapper and filesystem writeback.

          
Group will not deleteIt is populated or has child groups.Read cgroup.events, cgroup.procs, cgroup.threads and directory children. Kill/move tasks, remove leaves first.

          
Container sees a restricted cgroup viewcgroup namespace and mount namespace hide the host hierarchy.Compare from host and container. This is expected containment, not necessarily a fault.

                  
pids.max reached “too early”Threads count as tasks; the shell, launcher and helper processes also consume entries.Compare pids.current, ps -eLf and pids.events.

          
Rootless Docker flags appear ignoredcgroup v2/systemd delegation requirements are not satisfied.Inspect docker info. A none cgroup driver means resource flags are not enforced.

          
Pod restarted after memory pressureCould be container OOM, liveness failure or another runtime reason—not automatically eviction.Use kubectl describe pod, container last state, events and node pressure conditions.

          
Requested cpuset differs from effective setAncestor restriction, CPU hotplug or partition constraints narrowed it.Read cpuset.cpus and cpuset.cpus.effective at every ancestor.
